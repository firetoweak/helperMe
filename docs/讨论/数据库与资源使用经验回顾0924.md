# 数据库与资源使用经验回顾（0924）

> 根据本次讨论整理的个人回顾。经验主要来自以前做过的多人使用的智能系统，不是当前项目的故障报告，也不是架构决策或待实现清单。

## 我踩过的坑

以前把模型调用、数据库和多进程放到一起时，遇到过内存持续增长、进程没有及时退出、数据库访问积压，以及整个应用变得很卡的情况。还有一次，数据库锁和模型调用资源互相等待，结果模型迟迟没有真正被调用。

这些现象确实发生过，但现在没有当时的代码和测量记录，不能把每次卡顿都归因于连接耗尽，也不能把内存不回落都归因于泄漏。值得留下的是排查方向和设计经验。

## 留下的经验

1. **资源要有明确的释放责任。** 数据库连接、文件句柄、子进程，在正常结束、异常和取消时都要清理。Python 的 `with sqlite3.connect(...) as conn:` 处理事务提交或回滚，不负责关闭连接；需要显式关闭或使用 `contextlib.closing()`。

2. **事务要短，不跨模型或网络等待。** 先用短事务读取、认领并提交，释放数据库资源后调用模型，再用短事务校验提交条件、写入结果。长连接不等于长事务，不能把连接复用本身视为错误。

3. **排他锁谨慎使用。** 锁只保护必须原子完成的读写，缩小范围和持有时间。尤其注意资源获取顺序，避免一边持有数据库锁等模型名额，另一边持有模型名额等数据库，形成循环等待。

4. **保证正确，不等于不断重新查库。** 高频访问、重复全量读取和过多的小事务，都可能让处理速度赶不上请求速度。需要保留必要的一致性校验，同时避免无意义的重复工作；加连接、加线程不一定能解决积压。

5. **既看累计占用，也看峰值和并发。** 没释放是一类问题；每个任务最终都能释放，但同时跑太多、一次读入太大，是另一类问题。多进程提供隔离，也会叠加内存、CPU 和磁盘 IO 消耗。

6. **理解原则不等于代码已经做到。** 功能跑通、AI 能解释设计，都不能证明系统没有这些问题。判断应落在具体代码路径和验证证据上，区分已有保障、潜在风险和已经复现的故障。

## 放到当前个人助手里怎么看

以前的多人服务和现在单机运行的个人助手，负载差别很大。资源正确释放、避免循环等待、事务不跨慢调用，是基本要求；并发额度、连接复用和增量读取等策略，要根据实际场景决定，不照搬多人服务的整套治理机制。

单用户也可能通过多个子 Agent、大文件和长期运行放大消耗，但可能发生不等于现在必须增加限制。本次提到的 Worker 与工具并发规模、历史重复全量读取、文件枚举的峰值内存，先作为代码审查的关注点保留，不据此认定当前系统已经有故障。

当前只记录，不改实现、不做压测。以后需要验证时，可以用固定的小规模负载观察资源增长、峰值和结束后的回收，不以压垮机器作为验证目标。

这些属于软件工程的基础议题，但这份回顾的价值，是把自己遇到的具体问题整理成下次能识别、能解释的经验，而不是背下一套适用于所有系统的规则。
