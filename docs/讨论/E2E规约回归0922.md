# 2026-09-22 复杂 E2E 与规约回归

本轮使用隔离运行目录、真实模型和浏览器交互，覆盖并发 SubAgent、长工具链、连续 Compact、编辑分支、授权拒绝及服务重启。随后用确定性测试复核发现；浏览器观察与根因结论分别记录，不能仅因某次点击无响应就判定产品实现错误。

## 已修复：前置检查与决策输入的版本一致性

原路径是 Scheduler 完成容量检查，再调用 Runtime 重新读取 Journal 冻结 DecisionFrame。两次读取之间，新消息或 SubAgent 回报可以入账；旧检查结果因此可能放行包含新事实的输入。

现在 Scheduler 在前置检查前记录 Journal 位置，调用 `advance(expected_journal_position=...)`。位置变化时 Runtime 不认领 Step、不调用模型、不消费 trigger，Scheduler 下一次激活重新检查。目录同步或 Compact 发布改变事实位置时同样重新检查。冻结之后到达的事实仍只进入后续 Step，输入接纳不被长时间锁住。

这条约束属于“检查依据与执行依据一致”，Runtime 只理解事实位置，不理解 Compact、预算或任务语义。回归测试分别守 Runtime 的版本前提，以及 Scheduler 在检查期间收到 child report 后必须重新检查的契约。

同时发现容量预检查没有计入当次新增 LoopGuard 提醒。现在预检查与 Decision 使用相同的提醒组装方法；预检查只评估，不把未提交提醒写入冻结历史。已有重复调用测试核对预检查估算与实际模型请求估算一致。

16K 真实场景出现过源会话超预算和 Reader 超预算；上述竞态已由确定性测试覆盖，但现有日志不能证明所有超预算失败都由同一竞态造成。Reader 独立预算不足仍按现有规约失败，不声称本次已消除所有容量问题。

## 纠正定级：重启后待授权按钮无响应

浏览器观察：服务重启后恢复 `write_file` 的参数、command identity 和待授权状态；点击拒绝后未见授权 POST。Journal 中命令没有授权、拒绝或执行终态，目标文件不存在。随后 Computer Use 自身连接失败，无法继续独立浏览器复现。

初次报告将其定为确定 P1 缺陷，证据不足，撤回该定级。本轮新增两条回归测试：

- 真实 Conversation / ExecutionProcess 组件和 API mutation 在断线重连后，使用新 connection id 提交拒绝；不依赖 `authorization_required` SSE，返回投影后移除按钮。
- 真实 Host / Worker 重启后，WebChannel 从 Journal 恢复 pending command，按同一个 command id 拒绝；拒绝进入 Journal，文件未创建，会话继续回答。

两条测试均通过，当前没有依据修改授权生产链路。浏览器无响应保留为待复测项，不能据此认定 Runtime 丢状态，也不能认定已经找到浏览器卡顿根因。

## 保留的设计风险：Reader 工具可见性

长代码审查触发 Compact 后，真实 Reader 调用了 `read_file`，执行边界报 `InvalidLLMResponse`。当前规约要求 H 继承原 SYS / TOOLS 以保持冻结前缀，但只准执行 `read_compact_source`，因此该失败符合规约。

这是模型可见能力与执行许可不一致的质量风险。调整工具列表会影响前缀稳定性设计，需在 Compact 专题中明确取舍；本轮保留现有契约，不增加自动重试或吞异常路径。
