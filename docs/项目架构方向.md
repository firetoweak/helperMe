# 个人助手的可控扩展

> 长期原则。用于校准方向，不是逐条军令。
> 当前实现边界以 [架构总览](架构/总览.md) 和 [Runtime 状态推进模型](架构/Runtime状态推进模型.md) 为准。

## 立场

HelperMe 是个人拥有、理解并持续塑造的通用助手，不是面向未知用户的 Agent Framework。学习是构建方式，结果仍应能长期使用。

核心问题：

> 新增一个对个人助手有价值的功能时，能否局部接入、明确生效、独立验证，并且不引入服务于未知使用者的通用机制？

## 最高原则

> 功能能够持续生长，而复杂度仍由一个人掌控。

Runtime 不能比模型“更聪明”，也不能在隐藏路径中替模型做语义判断。Runtime 只负责确定性的事实归约、调度、不变量校验和安全边界；目标是否满足、事实意味着什么、下一步做什么，必须由模型、显式 Judge 或用户作出并留下事实。

- 认知掌控：能解释当前行为为何发生。
- 运行掌控：状态、权限、能力激活和失败不会暗中发生。
- 演化掌控：变化时知道改哪里、如何生效、如何验证。

高内聚是同一变化原因集中；低耦合是一个需求少扩散；可扩展是规划中的功能到来时只改局部。

每项重要抽象应能说出主要理由：Product（没有它场景完不成）、Architecture（没有它变化会扩散）、Exploration（主动实验）。探索性抽象不应未经验证就成为主链路负担。

## 扩展范围

```text
已经遇到的需求        立即设计并验证
路线中明确将做的功能  保留接入方向，不预建完整框架
想象中的可能性        暂不抽象
第三方未知需求        明确不负责
```

## 不同功能使用不同的窄端口

| 功能 | 变化原因 | 当前端口 |
|---|---|---|
| 决策与副作用 | 事实、推进、等待、恢复 | `helperme/runtime`：Event / Step / Command |
| 模型调用 | Provider 协议、连接与认证 | `helperme/llm`；配置只解析数据，具体客户端由 `helperme/bootstrap.py` 装配 |
| 文件与命令 | 路径、沙箱、执行 | `helperme/sandbox/` + `helperme/tools/` |
| 外部服务 | 发现、加载、调用 | Assistant ToolSurface：目录 + `load_toolset` |
| 指令包 | 按需读取，不增加执行循环 | `load_skill` / `read_skill_resource` |
| 完成判断 | 人定目标，模型补全标准 | Journal 中的 Criteria / Judgment |
| Web | 搜索、读取、浏览器 | 默认复用 MCP |
| SubAgent / Automation / Long Memory | 已确认方向、尚未实现 | 分别保留委派、外部唤醒、带来源记忆的窄接入方向，不预建统一框架 |

不因为“都是扩展”就做统一 Plugin 基类。MCP 与 Skill 已经证明变化方向不同。

## 目标目录

```text
runtime                 所有 Stream 必须遵守的运行不变量
assistant               HelperMe 决策、上下文、完成判定与 SubAgent 委派
automation              后台 Job、定时策略与外部唤醒
memory                  带来源的长期记忆提取、存储与检索
llm                     模型窄接口、路由、Provider Auth、LiteLLM Adapter
sandbox                 Workspace 与隔离执行边界
channels                CLI / IM 连续交互入口
tools / mcp / skills    按各自机制独立生长的模型能力
```

这是按变化原因确定的目标结构，采用分片迁移，不为了目录整齐一次性重写稳定代码。`platform`、`capabilities` 不作为宽泛物理目录：前者会混合 LLM、Sandbox、Channel，后者会错误暗示 Tool、MCP、Skill 共用一套扩展机制。

Channel 或 Automation 选择 Stream identity；`helperme/assistant/streams.py` 接收给定 identity 的应用操作，`helperme/runtime` 负责实际创建、持久执行、重放与机械恢复。

SubAgent 复用普通独立 Stream，父子委派属于 `assistant`；Automation 只向明确 Stream 追加唤醒事实；Long Memory 从 Journal / Artifact 派生带来源知识，并在 Decision Context 开始时冻结检索结果。三者都不扩张 Runtime 的语义判断。

MCP、Skill 可各自删除。删除后不得在 Runtime 留下它们的名词或生命周期；生产代码不保留泛化 `plugins/` 包。

## 可控扩展

1. **变化局部**：一个功能有明确主人。
2. **生效路径明确**：从配置到模型可见能力能说清；哪一层没生效要留下事实。
3. **结果可验证**：测功能，也测装配路径。
4. **失败可定位**：保留原始语义，不把错误吞成“能力不可用”。
5. **复杂度可移除**：删能力时，领域状态和专属分支一起删。

异常处理遵循“内部相信契约，外部精确转换”：纯内部调用链不使用宽泛异常捕获兜底，契约违规和未预期异常直接暴露；CLI 输入、模型响应、网络协议、文件系统等外部边界只捕获已经识别且能够给出确定处理结果的错误。未知异常不得被改写为普通 Outcome、能力不可用或可继续运行状态。持久化 Attempt 因进程失败停在 `unknown`，属于重启后的恢复事实，不是同一进程吞掉异常的理由。

### 代码实现原则：内部相信契约

- 外部数据只在进入系统的位置校验一次：工具参数、CLI JSON、LLM / MCP 响应、配置文件、Registry / Journal 反序列化和文件系统结果。schema 必须精确，禁止用缺省值、truthy、`str()` / `int()` / `bool()` 强转掩盖缺字段或类型错误。
- 数据一旦成为内部类型，消费者直接按契约读取。内部不存在“字段缺失就跳过”“未知命令就当普通失败”“ malformed fact 就返回 `None`”等兜底；这些情况必须立即抛出，暴露生产者或持久化损坏。
- Adapter / handler 只捕获它能够确认语义的闭合集合，例如参数校验失败、已知 Provider 错误、`OSError` 或明确协议解析错误，并转换成确定 Outcome。未列入集合的异常原样穿透。
- `except BaseException` 只用于取消后的资源清理、事务回滚或并行错误聚合；完成清理后必须重新抛出原异常，清理也失败时保留两者。禁止在宽泛 handler 中 `return`、`continue`、`break` 或 `pass`。
- 持久格式只接受当前版本和完整字段，不兼容旧 envelope，不自动补 revision、时间或状态。文件不存在可以是显式空状态；文件存在但不符合契约就是错误。
- 架构测试扫描上述宽泛异常规则；边界测试分别证明已知外部失败被确定转换、未知内部错误会穿透。

当前生效路径：

```text
Host 装配 Binding / Schema
  → 未加载的 Toolset 只有目录 + load_toolset
  → load_toolset 成功结果记录 toolset_id + revision
  → Assistant ToolSurface 据此维护或重建可丢弃缓存，并 runtime.bind_tool
  → 下一 Step 的 tools 列表才出现具体工具
```

## 明确不做

- 不为统一而把 MCP、Skill、判定收成一个 Plugin 框架。
- 不把 Turn 做成执行量子。
- 不把模型判断当作副作用安全边界。
- 不把投影缓存或 Checkpoint 当成第二事实源。
- SubAgent、Automation、Long Memory 在各自专题设计确认前，不预建领域状态机或统一增强能力框架。
