# 异步工具执行链回补总结

## 目标

在接入 MCP 前，将外部执行主干统一为连续的异步调用链，同时保持既有工具批次、Evidence、Artifact 外置和 StopGuard 语义。

```text
AgentApplication
    ↓ await
SessionRuntime
    ↓ await
RunRuntime
    ├─ await ModelCallService → LLMClient
    └─ await ToolsExecutor → ToolSpec.handler
```

纯内存领域计算继续同步；异步化不是工具并发化。

## 核心结论

- `AgentApplication.start/resume/execute`、`SessionRuntime.start/resume`、`RunRuntime.run`、上下文摘要、模型调用和工具执行统一为 async。
- `ToolSpec.handler` 收敛为严格的异步契约，不在 `ToolsExecutor` 中保留同步/异步隐式双轨。
- 模型工具批次仍按返回顺序逐个 `await`，不使用 `gather`。
- 每个工具完成后依次记录完整 Evidence、执行 Artifact 外置并写入 `ToolsState`；批次完成后才写 Conversation、Checkpoint 并检查中断和 StopGuard。
- 中断仍只设置 `RunControl` 标记，不取消当前工具 Task；当前批次完成后才进入安全停止判断。
- handler、模型客户端和内部装配异常保持原始异常传播；只在既有外部输入边界返回预期错误。
- PowerShell Runner 使用原生异步子进程，超时后终止进程树并等待退出，避免 Run 已结束但子进程继续修改文件。
- Goal 的 Contract、Executor、Judge 多 Run 链路同步改为 async，没有建立同步 RunHost 旁路。
- `AgentApplication` 通过通用异步资源上下文拥有 Application 级基础设施；Composition 可注入资源，但 Core 不引用 MCP。
- `asyncio.run()` 只存在于 Console 和独立 benchmark 的最外层入口，不进入 Runtime、Tool 或 Plugin 内部。

## MCP 后续接入点

MCP Plugin 可将 Application 级、懒连接的 Connection Manager 作为 `application_resources` 注入。Run 继续只拥有 Toolset 选择状态和 ToolSpec 快照；物理连接由 Application 关闭时统一释放。

本次只完成通用异步前置，不引入 MCP 协议、配置或连接实现。

## 验证

- Core、Goal Plugin 自动化回归全部通过。
- 覆盖同步语义迁移、严格异步 handler、异常传播、工具批次安全点、Context Summary、Goal Loop、异步 CLI 子进程和 Application 资源逆序关闭。

## 审计后发现的未闭合边界（2026-08-12）

本次回补已经贯通异步主链，但测试全绿不代表 Application 资源生命周期、Task 取消语义和 Run 期 Toolset 快照已经闭合。继续实现 MCP 前必须处理以下技术债。

### P1 · Run 期 Toolset 尚未形成稳定快照

`RunRuntime` 当前在每轮开始时，对所有已加载 Toolset 再次调用 `ToolsetProvider.tool_specs()`。这会把 Application 级最新目录直接投影进正在执行的 Run：若 MCP 工具目录或 Schema 在 Run 中途更新，同一 Run 已经见过的工具契约可能发生变化。

目标边界：

- Application 维护最新 MCP 目录及版本；
- Run 调用 `load_toolset` 成功时捕获一次 `ToolSpec` 快照；
- 当前 Run 后续轮次只复用该快照；
- 新目录版本只影响之后加载的 Toolset 或新的 Run。

### P1 · asyncio Task 取消会遗留幽灵 Session

`SessionRuntime._begin_and_execute_run()` 只捕获 `Exception`，不能处理 `asyncio.CancelledError`。实测取消正在执行的 Run 后：Session 和 RunRecord 仍为 `running`，`ended_at` 仍为空，但 `active_controls` 已被 `finally` 删除，状态与真实执行不一致，也无法通过正常 interrupt/resume 恢复。

目标边界：必须显式定义 Task 取消对应的状态迁移与 RunRecord 落账，完成清理后原样重新抛出取消异常。不得把取消静默转换成普通失败。

### P1 · Application 资源上下文可被绕过

Application 资源只在 `async with application` 中启动，但 `create_session/start/resume/execute` 在进入前、退出后仍可调用；重复进入还可能覆盖第一次创建的 `AsyncExitStack`。部分 benchmark 目前也直接调用 `application.start()`，没有进入 Application 上下文。

接入 MCP 后，这会造成未启动 ConnectionManager 就执行 Tool，或 Application 已关闭后继续使用连接。目标边界：Application 必须拥有显式生命周期状态，拒绝未启动、重复进入和关闭后的业务调用；关闭时不得悄然拆除仍被活动 Run 使用的资源。

### P1 · PowerShell Task 取消不会保证回收进程树

`PowerShellCommandRunner.run()` 当前只在超时时终止进程树。若等待进程、读取 stdout/stderr 或上层 Run 时 Task 被取消，子进程和 reader task 可能遗留，并在 Run 已结束后继续修改 Workspace。

目标边界：进程树终止、reader task 收束和 `proc.wait()` 必须覆盖超时、取消及内部异常路径；清理后保留原始异常或取消语义。

### P2 · Async LLM Client 未纳入 Application 资源所有权

`LLMClient` 已改用 `httpx.AsyncClient` 与 `AsyncOpenAI`，但当前没有关闭接口，也没有进入 Application Resource。连接池生命周期因此没有与 Application 对齐。

目标边界：明确内部创建与外部注入两种所有权；由 HelperMe 创建的异步 Client 在 Application 退出时关闭，外部注入的 Client 不得被擅自关闭。

### P2 · 部分 async Tool Handler 仍阻塞事件循环

`get_changes` 仍使用同步 `subprocess.run`；`grep` 仍使用同步 `subprocess.Popen` 和阻塞读取。它们虽然声明为 async handler，但执行期间会阻塞整个事件循环，影响其他 Session、MCP 连接通知和安全中断响应。

目标边界：耗时外部进程使用原生 asyncio subprocess；短小的本地文件操作暂不为了形式上的全异步而复杂化。

### P2 · JSON Schema Tool 的顶层 object 契约未前置验证

`JsonSchemaParameters` 会接受顶层 array 等合法 JSON Schema，但 `ToolsExecutor` 又统一要求工具参数必须是 JSON object。这会让内部不兼容 Schema 成功注册，随后每次调用都被伪装成外部输入错误。

目标边界：Tool 参数契约在构造阶段验证为模型 function-calling 与 MCP Tool 输入都可接受的顶层 object Schema；非法内部契约直接失败，模型生成的非法实参才返回可修正 Tool Error。

### 补充的测试缺口

后续测试至少补充：

- Application 未进入、重复进入、退出后调用以及活动 Run 期间关闭；
- Run Task 取消后的 Session、RunRecord 和 active control 一致性；
- PowerShell 取消后的进程树与 reader task 回收；
- Toolset 在同一 Run 中保持 Schema 快照稳定；
- 内部创建的 Async LLM Client 随 Application 关闭；
- 非 object 顶层 Tool Schema 在注册边界直接失败。

审计时自动化结果为 Core 271 passed、1 skipped，Goal Plugin 16 passed；上述问题均属于现有测试未覆盖的生命周期和契约技术债。
