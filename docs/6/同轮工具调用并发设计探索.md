# 同一 Round 工具调用并发设计探索

## 问题

一次模型响应可以同时声明多个 Tool Call。由于这些 Call 在模型看到任何工具结果之前就已经一起生成，它们通常不存在“后一个 Call 读取前一个 Call 返回值”的数据依赖。

由此产生一个问题：既然没有返回值依赖，为什么当前 HelperMe 仍按顺序执行，而不是把同一 Round 的 Calls 全部并行执行？

## 核心结论

同一 Round 只能说明 Calls 通常没有返回值依赖，不能证明它们没有副作用依赖。

```text
返回值依赖
后一个 Call 是否需要前一个 Call 的执行结果

副作用依赖
多个 Call 是否读取或修改同一份外部状态
```

例如下面两个读取彼此独立，适合并行：

```text
read_file("a.py")
read_file("b.py")
```

但以下 Calls 即使由模型在同一 Round 一起声明，仍存在业务顺序或共享状态冲突：

```text
write_file("config.json", content_a)
write_file("config.json", content_b)

apply_patch("app.py", patch_a)
apply_patch("app.py", patch_b)

npm install
npm test

git add .
git commit -m "change"
```

模型理论上应该把有依赖的操作拆成多个 Round，但 Runtime 不能以“模型永远正确”为并发安全前提。

因此合理原则不是“同轮 Calls 全部串行”或“同轮 Calls 全部并行”，而是：

> 只并行经过明确契约证明为并发安全的工具；未知工具和有副作用工具保持顺序。

## nanobot 的处理方式

nanobot 会启用并发工具执行，但不会直接对整个 Call 列表执行一次无条件 `asyncio.gather()`。

工具默认通过以下属性表达并发能力：

```text
read_only
concurrency_safe
exclusive
```

默认关系是：只读且非独占的工具才是 `concurrency_safe`。Runner 保持模型返回的 Call 顺序，将连续的安全工具组成并发批次；不安全或独占工具单独成为一个批次。

例如：

```text
read_file(a)
read_file(b)
write_file(c)
read_file(d)
read_file(e)
```

会被划分为：

```text
批次 1：read_file(a) + read_file(b)  并行
批次 2：write_file(c)                单独执行
批次 3：read_file(d) + read_file(e)  并行
```

并发批次使用 `asyncio.gather()`，其返回值仍保持输入顺序，因此执行完成时间可以不同，但工具结果写回顺序保持稳定。

这种设计同时保留了吞吐量、执行确定性和副作用边界。

## HelperMe 当前为什么保持顺序

HelperMe 正在把外部执行主干统一为 async。异步化首先解决的是：

- 模型、MCP 和子进程等待期间不阻塞事件循环；
- 外部资源能够正确超时和清理；
- MCP、CLI 和本地工具具有统一的异步 ToolHandler 契约；
- 未来可以建立明确的取消传播语义。

这些目标不要求同一批工具立即并发。

当前工具批次还包含多种会修改 Run 内外状态的工具：

- 文件写入和 Patch；
- CLI 与 Git；
- Todo Runtime Tool；
- `load_toolset`；
- 未来语义未知的 MCP Tool；
- Evidence、Artifact、ToolsState 和 Conversation 的结果记录。

如果在异步化阶段同时引入工具并发，就必须一起定义共享状态竞争、部分失败、结果落账、中断安全点和资源上限。这样会把两个独立问题耦合在一次改造中。

所以当前选择是：

```python
for call in calls:
    result = await tools_executor.execute(...)
```

这不是认定 Calls 一定具有前后依赖，而是暂时采用保守、确定的执行语义，让异步主干先稳定下来。

## 无条件并行的主要问题

### 共享状态冲突

两个工具可能同时修改同一文件、Git Index、数据库记录、Todo 状态或远程资源，最终结果取决于事件循环和外部系统的调度时序。

### 部分失败语义

若十个副作用工具同时启动，其中一个失败时，其余工具可能仍在改变外部状态。Runtime 很难明确本批次已经完成了哪些行为，以及是否还能安全继续。

### 中断与协议安全

HelperMe 当前在完整工具批次完成、结果进入 Evidence、Artifact、ToolsState 和 Conversation 后检查 `RunControl` 与 StopGuard。并发会要求重新定义未完成 Call、取消中的 Call 以及部分结果的协议表示。

### 资源压力

模型可能一次生成大量网络请求、进程或大文件读取。无界并发会同时占用连接、进程、文件句柄和内存，因此即使工具本身并发安全，未来仍需要并发数量限制。

### 可复现性

顺序执行提供稳定的行为轨迹。工具并发若没有严格分类和稳定写回规则，会使测试、故障复现和 Evidence 审计变得困难。

## HelperMe 后续可采用的设计

异步主干和 MCP 接入稳定后，可以为 `ToolSpec` 增加显式并发契约。概念上可表达为：

```text
SAFE
允许与其他 SAFE 工具组成并发批次

SEQUENTIAL
保持原始顺序，单独执行

EXCLUSIVE
执行期间不能与其他工具重叠
```

初始分类可以保守设定为：

| 工具 | 默认分类 | 理由 |
| --- | --- | --- |
| `read_file`、`glob` | `SAFE` | 只读且结果相互独立 |
| `grep` | `SAFE` 或限流后的 `SAFE` | 只读，但可能消耗较多进程和 I/O |
| `write_file`、`apply_patch` | `SEQUENTIAL` | 会修改 Workspace |
| Todo Runtime Tool | `SEQUENTIAL` | 修改当前 Run 的控制状态 |
| `load_toolset` | `SEQUENTIAL` | 修改本 Run 的可见工具快照和资源状态 |
| CLI、Git 写操作 | `EXCLUSIVE` | 副作用范围难以静态推断 |
| MCP Tool | 默认 `SEQUENTIAL` | 不能根据名称猜测远程副作用 |

MCP 工具只有在 Server 提供可信的只读/幂等 Annotation，且 HelperMe 明确接受该 Annotation 作为并发契约后，才可提升为 `SAFE`。未知工具必须保守处理。

Runner 可以继续按照原始 Call 顺序划分批次：

```text
连续 SAFE Calls
    → 有上限地并行执行

SEQUENTIAL / EXCLUSIVE Call
    → 先收束前一个并发批次，再单独执行
```

并发执行只改变工具运行的重叠关系，不应改变：

- Tool Result 在 Conversation 中的原始 Call 顺序；
- Evidence、Artifact 和 ToolsState 的语义；
- 工具输入校验和异常传播边界；
- RunControl 与 StopGuard 的安全停止要求。

## 当前阶段决策

当前不实现 Calls 并发，继续保持同一 Round 内逐个 `await`。

完成以下前置后，再把并发作为独立阶段设计和验收：

- 端到端异步执行主干稳定；
- MCP Run 期资源生命周期闭合；
- CLI 在超时、取消和异常路径下能可靠回收进程树；
- Toolset 快照、Evidence、Artifact、Conversation 与 StopGuard 的现有语义完成回归验证；
- `ToolSpec` 具备明确、可审计的并发安全契约；
- 定义并发上限和部分失败行为。

最终原则：

> Async 解决等待与资源生命周期；Concurrency 解决吞吐量。两者是不同设计问题。同一 Round 没有返回值依赖，只是允许探索并发的必要条件，不是全部 Calls 可以安全并发的充分条件。
