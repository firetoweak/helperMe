# 同一 Round 工具调用并发设计探索

## 问题

一次模型响应可以同时声明多个 Tool Call。由于这些 Call 在模型看到任何工具结果之前就已经一起生成，它们通常不存在“后一个 Call 读取前一个 Call 返回值”的数据依赖。

由此产生一个问题：既然没有返回值依赖，为什么当前 HelperMe 仍按顺序执行，而不是把同一 Round 的 Calls 全部并行执行？

## 核心结论

同一 Round 只能说明 Calls 通常没有返回值依赖，不能证明它们没有副作用依赖。

```text
返回值依赖
后一个 Call 是否需要前一个 Call 的执行结果

副作用依赖
多个 Call 是否读取或修改同一份外部状态
```

例如下面两个读取彼此独立，适合并行：

```text
read_file("a.py")
read_file("b.py")
```

但以下 Calls 即使由模型在同一 Round 一起声明，仍存在业务顺序或共享状态冲突：

```text
write_file("config.json", content_a)
write_file("config.json", content_b)

apply_patch("app.py", patch_a)
apply_patch("app.py", patch_b)

npm install
npm test

git add .
git commit -m "change"
```

模型应当把有依赖的操作拆成多个 Round；同一 Round 则视为模型明确给出的并行意图。

当前采用的核心原则是：

> 不要让 Runtime 比模型聪明。模型负责语义正确性，Runtime 负责执行正确性。

Runtime 不根据工具名称、命令文本或业务含义猜测调用 DAG，也不把同轮调用静默改成自认为正确的执行顺序。模型若错误地把存在状态依赖的操作放进同一 Round，由后续工具结果和下一轮模型调用负责纠错。

## nanobot 的处理方式

nanobot 会启用并发工具执行，但不会直接对整个 Call 列表执行一次无条件 `asyncio.gather()`。

工具默认通过以下属性表达并发能力：

```text
read_only
concurrency_safe
exclusive
```

默认关系是：只读且非独占的工具才是 `concurrency_safe`。Runner 保持模型返回的 Call 顺序，将连续的安全工具组成并发批次；不安全或独占工具单独成为一个批次。

例如：

```text
read_file(a)
read_file(b)
write_file(c)
read_file(d)
read_file(e)
```

会被划分为：

```text
批次 1：read_file(a) + read_file(b)  并行
批次 2：write_file(c)                单独执行
批次 3：read_file(d) + read_file(e)  并行
```

并发批次使用 `asyncio.gather()`，其返回值仍保持输入顺序，因此执行完成时间可以不同，但工具结果写回顺序保持稳定。

这种设计同时保留了吞吐量、执行确定性和副作用边界。

## HelperMe 此前为什么保持顺序

HelperMe 正在把外部执行主干统一为 async。异步化首先解决的是：

- 模型、MCP 和子进程等待期间不阻塞事件循环；
- 外部资源能够正确超时和清理；
- MCP、CLI 和本地工具具有统一的异步 ToolHandler 契约；
- 未来可以建立明确的取消传播语义。

这些目标不要求同一批工具立即并发。

当前工具批次还包含多种会修改 Run 内外状态的工具：

- 文件写入和 Patch；
- CLI 与 Git；
- Todo Runtime Tool；
- `load_toolset`；
- 未来语义未知的 MCP Tool；
- Evidence、Artifact、ToolsState 和 Conversation 的结果记录。

如果在异步化阶段同时引入工具并发，就必须一起定义共享状态竞争、部分失败、结果落账、中断安全点和资源上限。这样会把两个独立问题耦合在一次改造中。

所以异步主干回补阶段的选择是：

```python
for call in calls:
    result = await tools_executor.execute(...)
```

这不是认定 Calls 一定具有前后依赖，而是当时暂时采用保守、确定的执行语义，让异步主干先稳定下来。该阶段完成后，同轮并发作为独立改造落地。

## 无条件并行的主要问题

### 共享状态冲突

两个工具可能同时修改同一文件、Git Index、数据库记录、Todo 状态或远程资源，最终结果取决于事件循环和外部系统的调度时序。

### 部分失败语义

若十个副作用工具同时启动，其中一个失败时，其余工具可能仍在改变外部状态。Runtime 很难明确本批次已经完成了哪些行为，以及是否还能安全继续。

### 中断与协议安全

HelperMe 当前在完整工具批次完成、结果进入 Evidence、Artifact、ToolsState 和 Conversation 后检查 `RunControl` 与 StopGuard。并发会要求重新定义未完成 Call、取消中的 Call 以及部分结果的协议表示。

### 资源压力

模型可能一次生成大量网络请求、进程或大文件读取。无界并发会同时占用连接、进程、文件句柄和内存，因此即使工具本身并发安全，未来仍需要并发数量限制。

### 可复现性

顺序执行提供稳定的行为轨迹。工具并发若没有严格分类和稳定写回规则，会使测试、故障复现和 Evidence 审计变得困难。

## HelperMe 当前设计

同一模型响应中的全部 Calls 立即并发执行，不建立 `SAFE / SEQUENTIAL / EXCLUSIVE` 静态分类，也不由 Runtime 推断资源冲突：

```text
模型同一 Round 声明 Calls
    → 并发执行全部 Calls
    → 等待全部 Calls 收束
    → 按模型声明顺序提交结果
    → 下一轮由模型判断成功、失败与纠错
```

并发只改变工具运行的重叠关系，不改变：

- Tool Result 在 Conversation 中的原始 Call 顺序；
- Evidence、Artifact 和 ToolsState 的语义；
- 结构化工具失败不会取消同轮其他调用；
- handler 内部异常保持原始异常传播，但传播前等待兄弟调用全部收束，避免遗留后台副作用；
- 批次 Task 被取消时，取消传播至全部尚未完成的调用；
- RunControl 与 StopGuard 的安全停止要求。

Runtime 未来仍可增加纯机械执行约束，例如并发数量上限或底层连接的硬性互斥要求；这些约束不能演变为业务依赖推断。Prompt 必须明确要求模型把有先后依赖的调用拆到不同 Round。

默认 Agent Prompt 已加入对应执行契约：同一响应中的调用并发执行；Round 是执行屏障；独立操作应增加并行宽度；存在结果或副作用依赖时必须拆到后续 Round；发出同轮多调用即由模型确认其语义并发安全。

## 当前阶段决策

同轮 Calls 并发已经落地。批处理采用“并发执行、顺序提交”的两阶段结构；不修改 `ToolSpec`，并发意图直接由模型的 Round 边界表达。

仍需独立处理的技术债：

- `grep`、`get_changes` 等伪 async handler 仍会阻塞事件循环；
- PowerShell Task 取消时的进程树回收；
- Application、Session 取消后的生命周期一致性；
- MCP 接入后的连接级资源上限。

最终原则：

> Async 解决等待与资源生命周期；Concurrency 解决吞吐量。模型用 Round 表达语义依赖，Runtime 忠实执行并守住协议、取消、落账和资源生命周期边界。
