# 计划

从第 1 章起。当前架构已经闭合；下面是下一轮要做的事，不是旧 Phase 编号的续写。专题设计确认前不预建状态机。

校准：[项目架构方向](项目架构方向.md)、[Runtime 状态推进模型](架构/Runtime状态推进模型.md)。

判定上还挂着的两处见 [自主 Agent 学习计划](自主Agent学习计划.md#判定遗留)。

## 顺序

```text
1  get_changes     工作区变更核验重做
2  Level 2         增量摘要重做
3  Automation      定时 / 监听 / 后台唤醒
4  SubAgent        单个委派闭环
5  Memory          带来源的长期记忆
```

第 3～5 章复用现有 Stream / Journal / Step / Command。Runtime 不增加 Scheduler、父子 Agent 或 Memory 名词。

## 第 1 章 · get_changes

现有工具可继续用，核验语义要按新架构重做，不沿用 Git short status + unstaged diff 当完成证据。本章只占位，设计另开。

## 第 2 章 · Level 2

旧增量摘要不能直接搬到 Journal 投影上。摘要仍只能是投影，不能写回 Journal 当事实。本章只占位，设计另开。

## 第 3 章 · Automation

Agent 不只在同步对话里跑。

端口是 `automation`：外部按策略醒来，向**已经选定**的 Stream 追加事实。Channel 或 Automation 选 identity；Assistant 接收；Runtime 只负责追加后的推进与恢复。

| 能力 | 接法 | 第一刀 |
|---|---|---|
| 定时 | 时间策略追加 Timer 一类事实 | 延迟或 cron 唤醒一条已有 Stream |
| 监听 | 监听策略追加外部变化一类事实 | 文件或外部信号变化后醒来 |
| 后台 | 没有前台 Channel 时仍推进同一条 Stream | 进程里没有人盯着也能 `advance` |

不做：不在 Runtime 里预建 Job / Timer 状态机；不把后台做成第二种执行内核；没有真实定时需求时不建设通用调度平台。

先让「外部唤醒 → 追加事实 → 原 Stream 再决策」成立，再谈多条生命线同时泵。

## 第 4 章 · SubAgent

SubAgent 是**普通独立 Stream**。委派和回收属于 `assistant`，用因果 Event 表达；Runtime 不增加 `parent_stream_id`、`agent_type`。

```text
父 Stream 决定委派
        ↓
Assistant 创建子 Stream（同一套 create / advance / recover）
        ↓
子 Stream 自己的 Journal、工具、判定
        ↓
结果作为事实回到父 Stream，父再决策
```

第一刀只做**单个**委派闭环。没有两个以上真实并行工作者时，不先建协调层或共享状态。

不做：不恢复 TodoList 当跨 Agent 计划；不把多 Agent 收成 Runtime 内核能力；不为共享状态做第二事实源。

## 第 5 章 · Memory

从 Journal / Artifact 提炼带来源的知识，在 Decision Context **开始时冻结**检索结果。Journal 仍是嘈杂经历；Memory 是值得复用的派生，必须能指回事件。

```text
Journal / Artifact
        ↓
提取（带来源）
        ↓
存储与检索
        ↓
Step 开始时写入冻结 Decision Context
```

第一刀：带来源的提取 + 可选注入。向量检索、统一检索、遗忘都后置。

不做：不把 Journal 直接当长期记忆上下文；不让 Memory 写回 Runtime 当权威事实；没有消费者时不提前复制一套 facts。
