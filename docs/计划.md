## 后到 UserMessage 调度

2026-08-27 已落地。规范见 [Runtime 状态推进模型](架构/Runtime状态推进模型.md) 第 6 节。

没有独立 Interrupt Event。运行中与空闲输入都是 `UserMessageReceived`。归约两条机械规则：

1. 消息立刻入账；若签发 Step 的冻结视图早于这条消息，且已有未终态 Attempt，先等这批 Outcome，再把它当作可执行的 `next_trigger`。未派发（含待授权）不挡。同一轮已签发 Command 要跑完，不是再开一轮。
2. 签发冻结（`observed_journal_position`）早于这条消息的 `decision_on_outcome` 组，闭合后不再单独要 Step。下一次决策的 trigger 就是这条 UserMessage。后到相对冻结切面，即使消息写在该 `StepCommitted` 之前。

## 外部事实入口

2026-09-02 删除原第 4 章 Automation。「后台任务」不是一种机制，它把四件不同的事捆在同一个心理感受上：定时是外围脚手架，服务化是 Channel 接入与进程形态，SubAgent 是 Session 间因果，Kanban 是 Session 内判定。变化原因各不相同，合成一个框架就是预建统一后台机制。

留下的技术内容是一条公共链路：一条**不是人写的**外部事实如何进入 Journal、被幂等接纳、被模型看见，并按同一套规则参与决策。`DomainFactCommitted` 原本只是半通的，2026-09-02 补完，三处：

- **`DomainFactCommitted` 必须携带 delivery identity**，一律走 `accept_delivery`，不存在无 delivery 的版本。领域事实总有来源；强制之后幂等与可追溯是结构性的，不靠各处自觉。两个 Journal 的 `_validate_external_delivery` 各加一个类型，`_validate_generic_append` 各加一条拒绝，`MemoryJournal._restore` 的 external 集合同步；「外部必须有 delivery、内部必须没有」的双向约束原样保留。连带迁移：`AgentRuntime.record_fact` 走 `append`，在新规则下没有合法用途，删除，换成 `receive_domain_fact(session_id, fact_type, data, *, delivery_id, source, requests_decision, causation_id)`，不留双轨。
- 判据收敛为**外部决策事实**（`UserMessageReceived`，或 `requests_decision=True` 的 `DomainFactCommitted`），落成 `state._is_external_decision_fact`，五个调用点：`_requires_decision` 的入口与其 Outcome 段的抑制条件、在途 Attempt 的阻塞判据（`_user_message_blocked_by_in_flight` 随之更名 `_blocked_by_in_flight`），以及 `_include_waited_follow_up_events` 的两个调用点。不为新事实源开第二套规则。
- Assistant `_translate_visible_events` 原本只翻译三种 payload，`DomainFactCommitted` 被静默丢掉，Step 会在旧上下文里空转一次。协议只有四种 role 且 `tool` 必须对应 `tool_call_id`，领域事实只能进 `user`，但必须带明确标记不得伪装成人的发言；内容为 `{"fact": fact_type, "data": ...}`。投影 kind 仍记 `user`，保护窗因此把事实和人的消息同等对待——两者都是一轮的起点。

这条链路不独立排期，谁先需要谁推动。第一个有真实分量的用户是 SubAgent 的回收（已落地）：子 Session 结束后，结果作为父 Session 的一条非人事实回去。定时与文件监听是同一入口的其他可能源，不排期；真做时周期表达收窄成封闭小集合，不引入 cron 表达式（croniter 已停止维护，真需要时用 cronsim）。任何自动源的幂等键必须从触发本身派生，例如 `policy_id:scheduled_for`，不用 uuid；事实同时给出 `scheduled_for` 与 `fired_at`，迟到多久由模型判断，Host 不替它决定。

2026-09-02 确认：「人不在时仍推进同一条 Session」已由 Telegram 形态满足，不是待做项。Channel 接纳消息后立即返回，Scheduler 靠 Outcome 自行推进，`deliver` 回 chat，进程主循环不依赖任何人在场。

## 多活跃 Session

进程里藏着一个「一个进程一条活跃 Session」的隐含假设。它不是部署问题，是第 4 章的前置：父子 Session 必须同时活着。

阻塞第 4 章的两条，2026-09-02 补完：

- `deliver` 的 sink 原本是装配期传入的进程级回调，不分 Session、不分 reply route，子 Session 的输出没有去处。handler 本就拿得到 `context.session_id`，sink 签名改为 `(session_id, text)`，由 Host 维护 session_id 到 route 的映射，子 Session 映射到空操作。`SessionScheduler` 的 `notify` 同步改成同一签名——它在装配期本就和 sink 是同一个回调，两者一致后 Host 只需要一个路由函数。
- 失败传播原本是进程级：`SessionScheduler._record_failure` 一旦置位，所有 Session 的 wake 都抛，进程停止。一个子任务撞上限流会杀掉主对话。按错误类型分层，不一刀隔离：未预期异常保持进程级，那是 bug，必须暴露；已识别的模型错误降为 Session 级，它是外部边界的已知失败，只是单 Session 进程里区分它没有意义。判据直接复用 `assistant_failure_message`——认得出、能说人话的那批就是已识别，同一个函数顺带给出报给用户的措辞，不另立一张清单。降级后该 Session 停止自动推进但仍 `RUNNABLE`，错误报给它自己的 route，下一条外部事实从同一个 trigger 重试。

分层只覆盖 `advance` 这条路径，即模型决策本身。工具内部的模型调用（当前是 Skill diff 摘要）经 Dispatcher 冒泡，仍然进程级；那属于「工具异常不被包装、Attempt 保持 unknown」的既有语义，是另一件事。`LLMAuthenticationError` 也一并降为 Session 级：它虽然是进程配置问题、每条 Session 都会同样撞上，但留着进程比让 Telegram 直接失联好，且提示里已经写明改哪个字段。

不阻塞、记着待撞的两条：

- `runtime.bind_tool` 不带 session_id，`_tool_owners` 是进程级一张表。但跨 Session 的工具泄漏不会发生——`decision.py` 的 `allowed_tool_names` 校验是一道真闸，模型调用不在本 Session schemas 里的名字会被拒。残留问题只有两个 Session 加载「提供同名工具的不同 Toolset」时相互冲突，以及同名 binding 被后加载者覆盖；父子共用同一批 MCP server 时不触发。
- Channel 装配时把 session_id 焊死，一个进程只服务一条对话。子 Session 不属于任何 Channel，这条属于 Web 服务化。

控制面不在缺口内：`AssistantControlPlane` 的 `_staged` / `_pending` / `_active_sessions` 均按 session_id 分区，`ArtifactGateway` 有 `for_session`。

Web 前端与 FastAPI 服务化是这个假设的另一个使用者，不是新机制；它带来的额外内容只有真正的 Access 鉴权，四种 identity 的规则见 [Channel 接入契约](架构/Channel接入契约.md)。多进程共享同一 Journal 是另一件事：Journal 的 step claim lease 为多 worker 准备，但 Dispatcher 的在途 Attempt 与各类进程内缓存不是，未排期。

## 第 1 章 · get_changes

2026-08-23 完成。`get_changes` 是工作区快照证据，不替模型或 Judge 判断任务完成。

- tracked 正文统一读取 `HEAD → 最终工作树`，覆盖 staged 与 unstaged；
- untracked、binary 正文缺失和 diff 截断通过 `content_complete=false`、明细字段及 `limitations` 显式报告；
- 仓库尚无 HEAD 时保留状态，但明确报告基线不可用；
- 契约测试位于 `tests/tools/test_get_changes.py`。

不做 baseline 冻结、Agent 变更归因、通用 VCS 抽象或 Runtime 状态。

> 但事实上在聊天稍长的情况下（30-50轮），get_changes经常不被调用，模型有时会幻觉的认为 写/改 已经完成。

## 第 3 章 · 长任务

2026-08-24 结论：Kanban 与独立 Audit 放在同一专题设计。现有简单任务继续依靠「普通工具 Outcome 唤醒下一 Step；模型不再调用工具后进入 `WAITING(user_message)`」自然停机。

当前 `LifecycleIntent.COMPLETE` 和 Finalization Barrier 只是已实现并有测试覆盖的基础设施。生产 Channel 是持续 Session，不调用 `finalize()`；不在长任务专题前单独补触发。已落地的 [SubAgent](架构/SubAgent.md) 也没有复用终态协议——子 Session 就是普通 Session，「最多回收一次」由投递幂等保证，所以终态至今没有生产消费者。

更准确地说，`LifecycleIntent` 从未接通：Assistant 构造 `ModelDecision` 时从不设置它，`finalization_opportunity` 的第一道闸 `intent is LifecycleIntent.NONE` 使 `COMPLETE` 永不触发。走声明式完成得先补这个缺口，而「模型声明完成」正是已观察到会幻觉的那件事。

2026-09-02 补充：「监督线程」这个说法要拆开。Kanban 是**状态外化**，把有哪些事、各自到哪一步从模型记忆搬到可投影的事实上，治的是遗忘与漂移；完成判定是另一件事，治的是「声称完成却没核验」。后者的第一道防线应当是机械的——声称完成但本轮没有工作区证据事实，就不接受这个声称，这是 Finalization Barrier 那类条件的延伸，不需要第二个模型。语义判断（这些证据是否满足最初目标）才留给显式 Judge。若 Judge 做成独立 Session，它的结构与 SubAgent 相同，只是因果方向相反，不需要新机制。

定时唤醒不是长任务的解药：上下文没变时醒来，模型还是同一个结论。见[外部事实入口](#外部事实入口)。
