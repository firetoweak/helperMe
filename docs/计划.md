## 后到 UserMessage 调度

2026-08-27 已落地。规范见 [Runtime 状态推进模型](架构/Runtime状态推进模型.md) 第 6 节。

没有独立 Interrupt Event。运行中与空闲输入都是 `UserMessageReceived`。归约两条机械规则：

1. 消息立刻入账；若签发 Step 的冻结视图早于这条消息，且已有未终态 Attempt，先等这批 Outcome，再把它当作可执行的 `next_trigger`。未派发（含待授权）不挡。同一轮已签发 Command 要跑完，不是再开一轮。
2. 签发冻结（`observed_journal_position`）早于这条消息的 `decision_on_outcome` 组，闭合后不再单独要 Step。下一次决策的 trigger 就是这条 UserMessage。后到相对冻结切面，即使消息写在该 `StepCommitted` 之前。

## 外部事实入口

2026-09-02 删除原第 4 章 Automation。「后台任务」不是一种机制，它把四件不同的事捆在同一个心理感受上：定时是外围脚手架，服务化是 Channel 接入与进程形态，SubAgent 是 Session 间因果，Kanban 是 Session 内判定。变化原因各不相同，合成一个框架就是预建统一后台机制。

留下的技术内容是一条公共链路：一条**不是人写的**外部事实如何进入 Journal、被幂等接纳、被模型看见，并按同一套规则参与决策。`DomainFactCommitted` 原本只是半通的，2026-09-02 补完，三处：

- **`DomainFactCommitted` 必须携带 delivery identity**，一律走 `accept_delivery`，不存在无 delivery 的版本。领域事实总有来源；强制之后幂等与可追溯是结构性的，不靠各处自觉。两个 Journal 的 `_validate_external_delivery` 各加一个类型，`_validate_generic_append` 各加一条拒绝，`MemoryJournal._restore` 的 external 集合同步；「外部必须有 delivery、内部必须没有」的双向约束原样保留。连带迁移：`AgentRuntime.record_fact` 走 `append`，在新规则下没有合法用途，删除，换成 `receive_domain_fact(session_id, fact_type, data, *, delivery_id, source, requests_decision, causation_id)`，不留双轨。
- 判据收敛为**外部决策事实**（`UserMessageReceived`，或 `requests_decision=True` 的 `DomainFactCommitted`），落成 `state._is_external_decision_fact`，五个调用点：`_requires_decision` 的入口与其 Outcome 段的抑制条件、在途 Attempt 的阻塞判据（`_user_message_blocked_by_in_flight` 随之更名 `_blocked_by_in_flight`），以及 `_include_waited_follow_up_events` 的两个调用点。不为新事实源开第二套规则。
- Assistant `_translate_visible_events` 原本只翻译三种 payload，`DomainFactCommitted` 被静默丢掉，Step 会在旧上下文里空转一次。协议只有四种 role 且 `tool` 必须对应 `tool_call_id`，领域事实只能进 `user`，但必须带明确标记不得伪装成人的发言；内容为 `{"fact": fact_type, "data": ...}`。投影 kind 仍记 `user`，保护窗因此把事实和人的消息同等对待——两者都是一轮的起点。

这条链路不独立排期，谁先需要谁推动。第一个有真实分量的用户是第 4 章 SubAgent 的回收：子 Session 结束后，结果要作为父 Session 的一条非人事实回去。定时与文件监听是同一入口的其他可能源，不排期；真做时周期表达收窄成封闭小集合，不引入 cron 表达式（croniter 已停止维护，真需要时用 cronsim）。任何自动源的幂等键必须从触发本身派生，例如 `policy_id:scheduled_for`，不用 uuid；事实同时给出 `scheduled_for` 与 `fired_at`，迟到多久由模型判断，Host 不替它决定。

2026-09-02 确认：「人不在时仍推进同一条 Session」已由 Telegram 形态满足，不是待做项。Channel 接纳消息后立即返回，Scheduler 靠 Outcome 自行推进，`deliver` 回 chat，进程主循环不依赖任何人在场。

## 多活跃 Session

进程里藏着一个「一个进程一条活跃 Session」的隐含假设。它不是部署问题，是第 4 章的前置：父子 Session 必须同时活着。

阻塞第 4 章的两条，2026-09-02 补完：

- `deliver` 的 sink 原本是装配期传入的进程级回调，不分 Session、不分 reply route，子 Session 的输出没有去处。handler 本就拿得到 `context.session_id`，sink 签名改为 `(session_id, text)`，由 Host 维护 session_id 到 route 的映射，子 Session 映射到空操作。`SessionScheduler` 的 `notify` 同步改成同一签名——它在装配期本就和 sink 是同一个回调，两者一致后 Host 只需要一个路由函数。
- 失败传播原本是进程级：`SessionScheduler._record_failure` 一旦置位，所有 Session 的 wake 都抛，进程停止。一个子任务撞上限流会杀掉主对话。按错误类型分层，不一刀隔离：未预期异常保持进程级，那是 bug，必须暴露；已识别的模型错误降为 Session 级，它是外部边界的已知失败，只是单 Session 进程里区分它没有意义。判据直接复用 `assistant_failure_message`——认得出、能说人话的那批就是已识别，同一个函数顺带给出报给用户的措辞，不另立一张清单。降级后该 Session 停止自动推进但仍 `RUNNABLE`，错误报给它自己的 route，下一条外部事实从同一个 trigger 重试。

分层只覆盖 `advance` 这条路径，即模型决策本身。工具内部的模型调用（当前是 Skill diff 摘要）经 Dispatcher 冒泡，仍然进程级；那属于「工具异常不被包装、Attempt 保持 unknown」的既有语义，是另一件事。`LLMAuthenticationError` 也一并降为 Session 级：它虽然是进程配置问题、每条 Session 都会同样撞上，但留着进程比让 Telegram 直接失联好，且提示里已经写明改哪个字段。

不阻塞、记着待撞的两条：

- `runtime.bind_tool` 不带 session_id，`_tool_owners` 是进程级一张表。但跨 Session 的工具泄漏不会发生——`decision.py` 的 `allowed_tool_names` 校验是一道真闸，模型调用不在本 Session schemas 里的名字会被拒。残留问题只有两个 Session 加载「提供同名工具的不同 Toolset」时相互冲突，以及同名 binding 被后加载者覆盖；父子共用同一批 MCP server 时不触发。
- Channel 装配时把 session_id 焊死，一个进程只服务一条对话。子 Session 不属于任何 Channel，这条属于 Web 服务化。

控制面不在缺口内：`AssistantControlPlane` 的 `_staged` / `_pending` / `_active_sessions` 均按 session_id 分区，`ArtifactGateway` 有 `for_session`。

Web 前端与 FastAPI 服务化是这个假设的另一个使用者，不是新机制；它带来的额外内容只有真正的 Access 鉴权，四种 identity 的规则见 [Channel 接入契约](架构/Channel接入契约.md)。多进程共享同一 Journal 是另一件事：Journal 的 step claim lease 为多 worker 准备，但 Dispatcher 的在途 Attempt 与各类进程内缓存不是，未排期。

## 第 3 章 · 长任务

2026-08-24 结论：Kanban 与独立 Audit 放在同一专题设计。现有简单任务继续依靠「普通工具 Outcome 唤醒下一 Step；模型不再调用工具后进入 `WAITING(user_message)`」自然停机。

当前 `LifecycleIntent.COMPLETE` 和 Finalization Barrier 只是已实现并有测试覆盖的基础设施。生产 Channel 是持续 Session，不调用 `finalize()`；不在长任务专题前单独补触发。未来明确有界的 SubAgent 或一次性后台执行可以显式复用终态协议。

2026-09-02 补充：「监督线程」这个说法要拆开。Kanban 是**状态外化**，把有哪些事、各自到哪一步从模型记忆搬到可投影的事实上，治的是遗忘与漂移；完成判定是另一件事，治的是「声称完成却没核验」。后者的第一道防线应当是机械的——声称完成但本轮没有工作区证据事实，就不接受这个声称，这是 Finalization Barrier 那类条件的延伸，不需要第二个模型。语义判断（这些证据是否满足最初目标）才留给显式 Judge。若 Judge 做成独立 Session，它的结构与 SubAgent 相同，只是因果方向相反，不需要新机制。

定时唤醒不是长任务的解药：上下文没变时醒来，模型还是同一个结论。见[外部事实入口](#外部事实入口)。

## 第 4 章 · SubAgent

SubAgent 是**普通独立 Session**。委派和回收属于 `assistant`，用因果 Event 表达；Runtime 不增加 `parent_session_id`、`agent_type`。

```text
父 Session 决定委派
        ↓
Assistant 创建子 Session（同一套 create / advance / recover）
        ↓
子 Session 自己的 Journal、工具、判定
        ↓
结果作为事实回到父 Session，父再决策
```

两个前置：回收路径需要[外部事实入口](#外部事实入口)，父子同时活着需要[多活跃 Session](#多活跃-session)中阻塞的两条。

2026-09-02 确认设计并落地，代码在 `helperme/assistant/subagent.py`。

### 价值

上下文隔离是主要理由，并行是次要理由。整个 `assistant/context/` 都在一条 Session 内部跟上下文膨胀作战——预算、保护窗、体积外置、Level 1 脱水，还欠着 Level 2；SubAgent 从另一个方向解同一个问题：让中间过程根本不发生在父的 Journal 里。因此全部设计围绕一件事——**父只拿结论，不拿过程**。任何一处冒泡都会漏掉隔离。

### 只读子 Session

子 Session 只拿只读白名单：`glob`、`grep`、`read_file`、`get_changes`、`read_artifact`、`load_skill`、`read_skill_resource`，以及 MCP 中的只读工具。排除 `apply_patch`、`replace_all`、`write_file`；`execute_command` 整个排除，因为无法静态判断一条命令是否只读。递归也用同一机制禁止：白名单里不给委派工具。

这不是保守选择。内置工具全部使用 `ToolSpec` 的 `requires_authorization` 默认值 `False`，当前只有 MCP 工具与控制面走授权闸；子 Session 一旦拿到写工具就是无闸直写。只读因此是当前唯一的安全边界，不是授权难题的妥协解法。

**单写者是委派树内的不变量，不是全局不变量。** 分界在于并行由谁制造：父决定开几个子，这个并行是 Agent 造的，用户没参与，Agent 必须为它负责；用户同时开两条顶层 Session 是在开两个完整任务，写冲突是用户的选择，Agent 不替他兜底。`get_changes` 的契约因此不需要改——它本就只报告工作区快照、明确不做变更归因；需要约束的只是子 Session 的工具白名单。

### 停机与回收

子 Session 是**没有人的 Session**：父落到 `WAITING(user_message)` 合理，因为真的有人会再说话；子落到同样状态则没人会来。由此得到纯机械的判据，不问模型做完没有，只看它还有没有事做：

| `waiting_for` | 含义 |
|---|---|
| `("user_message",)` | 本轮产出完毕，可以回收 |
| 含 `authorization:` | 卡在授权，需要冒泡，不是完成 |
| 含 `command:` | 还在跑，继续等 |

**父是子的 Judge。** 做得够不够由父判断，不够就向子追加一条消息，子重新 `RUNNABLE`。子 Session 因此不需要终态协议，它就是一条可反复唤醒的普通 Session。

这条路同时绕开了一个当前事实：`LifecycleIntent` 从未接通——Assistant 构造 `ModelDecision` 时从不设置它，`finalization_opportunity` 的第一道闸 `intent is LifecycleIntent.NONE` 使 `COMPLETE` 永不触发。走声明式完成得先补这个缺口，而「模型声明完成」正是已观察到会幻觉的那件事。

回收内容由子通过显式的 `report` 工具产出，那次调用的参数就是回收内容：产出成为有 schema 的事实而不是从散文里捞，同时避免成果上下文过长。子没调 `report` 就停机，则诚实回收一条「停机但无产出」。

观察静止的挂点是 `SessionScheduler._task_done` 中任务结束且无 pending wake 的那一刻，需要一个 hook。观察属于 assistant，Scheduler 不认识「子 Session」。

### 委派

委派必须异步：`delegate` 的 Outcome 只是「子 Session 已创建」，结果经外部事实入口回到父。同步版本把一条可能活很久的独立生命线塞进一个 Attempt 的生命周期，进程一崩就得到一个「未知副作用」，而它明明完好地躺在子的 Journal 里。

委派关系用因果事实表达：父的 `delegate` Outcome 记 `child_session_id`，子的初始事实记父 id，两边闭合。重启后扫父 Journal 投影重建未回收集合，模式照 `project_toolset_activations`。Runtime 不增加 `parent_session_id`、`agent_type`。

子 Session 的 deliver sink 是空操作，内容留在子自己的 Journal；初始上下文只有一段任务描述，不继承父的对话历史。任务本身以 `subagent.task` 事实进入子 Journal，不伪装成用户消息。子 Session 换用独立的 system prompt：它没有 Toolset 目录也不碰管理面，两份 catalog 都不拼；prompt 里写明没有人在另一端、report 是唯一出口。让用户看到子在做什么、让子访问父的上下文或 Journal，都是后续升级，不进第一版。

**并行委派要给父一个「齐了没有」的依据。** 一个 Step 里可以发多次 `delegate`，子 id 取自各自的 command id，天然不撞；子之间只读、互不感知，并行是安全的。但结论不是一次性交付的：每个子静止就单独回收一次，父被逐条唤醒。系统提示里「等这一组结果全部结束再综合判断」只约束同一 Step 的工具调用组，跨 Session 回灌的事实不在其中，Runtime 不会替父攒齐。父因此可能在只拿到一半结论时就下结论。所以父在决策时从自己已冻结的事实里投影出待回收集合（`project_pending` = 已委派 − 已回收），非空就往 system prompt 追加一句约束，让它别拿半份结论作答，而不是让模型自己数 Outcome。

**「还差谁」是派生值，不冻进事实。** 回收事实只记这个子自己的终局。若把「还差几个」算好写进事实，两个并行的子就必须在父维度串行读写才算得对：它们几乎同时静止，各自读父 Journal 再写入，无锁时都读到对方写入前的状态，双双报「还差一个」，父永远等不到 0。改成读时投影，事实只述自己、聚合留给读方，这个约束和那把锁一起消失。附带两个好处：投影读的是 `observed_journal_position` 冻结的那份事实，与决策看到的世界同一口径，重放一次早先的决策，那次子还没回来，约束照旧出现；提示只说「还没齐」不说「还差几个」，没有行为依赖这个数的大小，而带上它会让 system prompt 每收到一条结论就变一次，整段 prefix 缓存跟着失效。

读时投影唯一要担心的是漏人。`project_delegations` 读的是 `delegate` 的 Outcome，而 Outcome 在 handler 返回之后才提交，handler 里却已经唤醒了子；一个极快的子若在兄弟的 Outcome 落库前就回收，父会看到空集合并据此提前作答。测试守的就是这个交错——脚本模型不阻塞，两个子总是一个跑完再跑另一个，须让 snapshot 与写入都真正让出控制权。在此前提下，凡是已有结论回来的那一帧，兄弟的 Outcome 都已可见，投影不会漏人。

父子关系的进程内缓存必须能从 Journal 认回来，否则重启后子 Session 会失去只读边界——这是安全性质，不只是「委派丢了」。两个方向都要认：恢复父时从它的 `delegate` Outcome 找出子并唤醒未回收的那些，恢复子时从它自己的 `subagent.task` 事实找回父。只做前者的话，直接 `/resume` 一个子 Session 就绕过了整道边界。

**失败也是终局。** 子 Session 撞上已识别的模型失败时，它按[多活跃 Session](#多活跃-session)的分层停止自动推进——但那不是静止，`waiting_for` 里没有 `user_message`，回收不会发生。不补这条，父会拿着一个永远清不空的待回收集合一直等，而按上面的契约它此时还不该发言。

Scheduler 因此报告两种终局：静止（`on_quiesced`）与已识别的失败（`on_failed`）。两者语义不同，不合并成一个信号——Scheduler 只诚实说出发生了什么，是否算「一件事做完了」由订阅者判断。

回收事实增加 `failure` 字段，装 `assistant_failure_message` 的原文。失败**不改写含义**：不降级成「停机但无产出」，也不翻译成模型看不出所以然的错误码。父是 Judge，重派、换做法还是如实告诉用户，由它读了原因再定。失败与成功共用一条回收事实和同一个 `delivery_id`，`project_reclaimed` 因此自动认得，待回收集合天然清空；代价是一个子最多回收一次终局，失败后即使又被推进并静止，第二次回收会被幂等去重。

子 Session 的失败提示同样不外露：`notify` 与 deliver 一样经 `routed_sink`。用户该看到的是父转述后的判断，而不是一条不知来处的裸错误。父自己失败仍照常送达——拦的是子，不是所有失败。

### 后续

compact / summary：由子 Session 做 Level 级压缩，摘要成为**新 Session 的第一条事实**而非写回旧 Journal，旧 Journal 完整保留，然后把新 Session 晋升为主 Session。它比 Level 2 更彻底——Level 2 无论怎么压 Journal 仍在增长，换生命线才真正截断历史。难点在 Channel：Conversation identity 要求稳定，晋升需要代际编号（如 `...chat-{id}#2`，取最大代），使映射可从已有 session id 推导，不新增状态表。做成 SubAgent 的唯一站得住的理由是**摘要器需要工具**（脱水后内容在 artifact 里，需要 `read_artifact` 展开）；它的输入是另一条 Session 的 Journal，属于跨 Session 读取，普通 SubAgent 用不到。等本体完善后再设计。
