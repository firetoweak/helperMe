# 计划

本文记录 HelperMe 下一阶段要解决的架构问题。已经落地的结构与接口以[架构总览](架构/总览.md)为准，具体运行规则见[Runtime](架构/Runtime.md)。涉及边界调整时，以[项目架构方向](项目架构方向.md)校准。

当前架构已经闭合。后续功能复用现有的会话、事实记录、单步决策和命令执行机制；没有真实需求前，不提前增加领域状态机或统一框架。

## 判定遗留

- 将用户目标编译为可核验条件。目前仍使用“是否写过文件、是否运行过命令”这类固定模板。
- 无法确定用户是否更换目标时，主动请求用户确认。目前主要依赖关键词判断，其余输入默认延续当前任务。
- 独立 Judge 的真实模型调用与长任务的完成核验一起设计，不单独接通。

## 学习顺序

```text
1  工作区变更证据    已完成
2  对话上下文压缩    下一步
3  长任务            进度外化与完成核验
4  SubAgent          基础委派闭环已完成
5  Memory            带来源的长期记忆
```

## 第 1 章 · 工作区变更证据

已完成。模型可以取得从代码基线到当前工作区的完整变更，并明确知道哪些内容无法读取或被截断。这份证据只回答“工作区实际发生了什么”，不替模型判断任务是否完成。

> 仍然存在一个上层问题：对话稍长后，模型可能忘记主动核验变更，并误以为修改已经完成。这个问题属于长任务的完成核验，不继续扩张变更工具本身。

## 第 2 章 · 对话上下文压缩

长对话不能无限把全部历史交给模型，需要在保留关键事实的前提下压缩早期内容。

压缩结果只是给模型阅读的上下文，不是新的运行事实，也不能覆盖原始记录。原始经历始终可追溯；摘要丢失细节时，系统应当能够回到原始内容取证。

本章需要确定：

- 哪些近期内容必须原样保留；
- 哪些早期内容可以摘要，以及何时更新摘要；
- 摘要如何标明覆盖范围和来源；
- 模型如何按需展开被压缩的原始内容。

先完成这一层，再考虑通过更换主会话彻底截断历史。

## 第 3 章 · 长任务

长任务有两个不同的问题。

**进度外化**解决遗忘和漂移：把待办事项、当前进度和阻塞原因写成可重放的事实，模型不必只靠上下文记忆任务全貌。

**完成核验**解决过早宣布完成：模型声称完成时，系统先检查是否存在必要的客观证据，例如实际工作区变更和验证结果。证据是否满足用户目标仍是语义判断，应交给模型、独立 Judge 或用户，运行内核不替他们作结论。

现有简单任务继续自然运行：工具结果会触发下一步决策；模型没有下一步动作时，回到等待用户输入。定时唤醒不会让缺少新事实的任务变得更可靠，因此不作为长任务方案。

本章将 Kanban 与完成判定放在同一专题中设计，但保持两者职责分开。具体方案确认前，不接通声明式完成，也不增加独立 Judge。

## 第 4 章 · SubAgent

基础委派闭环已完成，当前设计见[SubAgent](架构/SubAgent.md)：主 Agent 可以把只读调查交给独立子会话；子会话自行工作，结论作为一条有来源的事实返回主会话。

后续可能用子会话完成深度压缩：它读取旧会话及相关产物，生成带来源的摘要，再由一个新会话接替旧会话。旧会话完整保留，新会话从摘要开始，从而真正截断持续增长的上下文。

这个方向暂不实施。它依赖第 2 章先明确摘要的内容、来源和展开方式，也需要解决同一对话跨会话延续时的稳定身份问题。

## 第 5 章 · Memory

Memory 保存值得跨任务复用的知识，原始会话记录仍保存完整经历。记忆由会话记录和产物提炼而来，必须能指回来源，不能成为无法核验的第二事实源。

```text
会话记录 / 产物
        ↓
提炼并保留来源
        ↓
存储与检索
        ↓
一次决策开始时冻结检索结果
```

检索结果在一次决策开始时确定，避免决策过程中上下文悄然变化。具体的提取时机、记忆结构、更新规则和检索策略留待本章设计。

## 后置专题

以下内容不属于当前学习主线。已有结论保留，剩余问题在真实需求出现或测量证明必要时再展开。

### Runtime 性能

运行记录是唯一事实源；上下文摘要不能兼任运行快照。未来若完整重放成为明确瓶颈，可以让快照记录自己覆盖到的位置，恢复时只重放之后的新事实。投影规则或事实结构变化时，旧快照必须明确失效。

是否调整数据库持久化策略或连接方式，应以测量结果为依据，不能用较弱的持久化保证换取未经证实的性能收益。

### 运行中到达的新消息

这一调度规则已经落地：新消息立即记入当前会话，但不会打断已经发出的工具调用。当前一轮结束后，新消息优先成为下一轮决策的起点，避免旧工具结果抢先触发一次基于过时上下文的判断。

取消当前工作、终止外部进程和通用中断协议尚未设计，它们是独立专题。

### 外部事实入口

系统除了接收人的消息，还需要接收子任务结果、定时触发或文件变化等外部事实。这些来源共用一条窄入口：事实必须说明来源，重复投递只能接纳一次，并明确它是否要求 Agent 继续决策。模型看到它时，也必须能区分外部事实与人的发言。

“后台任务”不作为统一机制。定时触发属于外围调度，服务化属于接入方式，SubAgent 属于会话间协作，Kanban 属于会话内的任务判断。它们变化原因不同，只共享外部事实进入会话的路径。

当前第一个实际使用者是 SubAgent 的结果回传。定时与文件监听不单独排期；将来实现时，由触发本身产生稳定的去重身份，并把计划时间和实际发生时间都交给模型判断。

### 多活跃会话

SubAgent 要求主会话与子会话能够同时运行。当前已支持按会话路由输出，也区分了单个会话可处理的模型错误与必须暴露的系统错误，因此一个子任务的已知外部失败不会停止其他会话。

仍有两个尚未遇到的限制：不同会话若加载同名但实现不同的工具，进程级工具绑定可能冲突；当前 Channel 装配仍面向一条主对话，不适合一个进程直接承载多个独立用户会话。前者等真实冲突出现时处理，后者归入 Web 服务化设计。

多进程共同执行同一批会话是另一个问题。现有持久层只为竞争领取工作保留了基础，不代表整个执行系统已经支持多进程部署。
