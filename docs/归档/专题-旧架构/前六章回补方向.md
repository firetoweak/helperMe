# Phase 0～6 回补方向

## 背景

Phase 0～6 的基础内容完成后，暂不进入后续阶段。当前实现暴露出两个需要回补的方向：执行历史和上下文脱水。TodoList 不再作为新架构的待评估项：旧 Turn `core/` 已删除，新栈不引入。

本文件只保留方向、优先级和相互关系；已经形成独立问题空间的内容进入单独专题，不在此展开架构设计。

## 优先级与关系

```text
Journal-backed Agent Runtime
        ↓ 提供统一的事实、推进与恢复语义
上下文脱水优化
        ↓ 提升长任务中的上下文持续性
后续后台任务 / SubAgent / Long Memory
```

前两项是当前关键方向。执行历史优先于脱水优化：如果不能固定并重放一次运行，也不能追踪信息如何产生、投影和消费，就无法可靠评价连续脱水后的运行质量。

新栈不并行观察 TodoList。它在旧架构里已经很难用；Journal 世界里「做过什么 / 做成是什么 / 能不能停」各有主人，再迁一份可改写清单会变成第二事实源。详见 [判定标准与 Judge 延后决策](判定标准与Judge延后决策.md)。

## 方向一：Execution Journal 与可重放执行历史

最初观察到的问题是 Trace 太简单，但进一步分析后发现，Trace 只是更底层问题的一个表现：系统缺少统一、持久、可关联和可重放的执行历史。

该方向最初升级为独立的 [Execution Journal 与可重放执行历史](Execution%20Journal与可重放执行历史.md) 专题；继续推演后，Journal 已从事后历史提升为新 Runtime 的事实骨架。目标架构见 [Agent Runtime 状态推进模型](Agent%20Runtime状态推进模型.md)。

当前方向是：以 Event 为持久事实、State 为归约、Step 为决策闭环、Command 为副作用闭环建立新 Runtime。L1 可观测、L2 可重放、L3 可恢复不再是不同架构或 L2 停止边界，而是同一核心模型的逐级验收能力。14.1 语义 MVP、14.2 Durable MVP、14.3 边界切片与 Completion / Termination Finalization Barrier 已于 2026-08-21 完成，实施边界见 [Agent Runtime 语义 MVP 实现总结](Agent%20Runtime语义MVP实现总结.md)、[Agent Runtime Durable MVP 实现总结](Agent%20Runtime%20Durable%20MVP实现总结.md)、[Agent Runtime 边界切片实现总结](Agent%20Runtime边界切片实现总结.md) 和 [Agent Runtime 终态与 Finalization Barrier 实现总结](Agent%20Runtime终态与Finalization%20Barrier实现总结.md)。

14.3 之后、Phase 7 之前，继续 **Runtime 接管 HelperMe 的收口工程**：把基座闭合并接回真实任务。不给 Runtime 增加 SubAgent、后台任务、Long Memory 或 Goal 新建模。判定标准 / 独立 Judge / continue 特权的产品策略见 [判定标准与 Judge 延后决策](判定标准与Judge延后决策.md)，实现总结见 [判定标准与 Judge 实现总结](判定标准与Judge实现总结.md)。

Runtime 终态语义已补上。其余尽量作为外围适配：Approval 决定为什么批准，Runtime 只消费授权事实；Artifact Store 提供内容，Replay 只持稳定引用；Turn 是 Projection / Product mapping；旧 HelperMe 通过 Adapter 接入，不把旧 Core 逻辑搬进新 Runtime。

```text
✓ Completion / Termination
        ↓
✓ 对照入口成为默认入口（console）
        ↓
✓ 眼下：Model Context 投影 + token 预算 + Artifact + 最近保护窗
        ↓
✓ 判定标准 / 独立 Judge / continue 特权
        ↓
✓ Host Toolset 渐进加载 + MCP（目录 / load_toolset / 下一 Step 才出现工具）
        ↓
✓ Skill 作为两个普通工具接到新栈 Host
        ↓
✓ Command 授权接线（Host yes/no → CommandAuthorized；SqliteJournal）
        ↓
✓ 删除 core / Turn 对照入口；Host 承接 LLM 与环境工具
        ↓
第 7 章
```

眼下路线的保护对象是上一句 `UserMessage` 之后的 Step/Outcome（与当前意图相关，不脱水）；窗外且已消费且成功的结果才 stub。摘要只做投影缓存，不写回 Journal。Turn 仍只是投影，不是执行量子。Approval 由 Host 决定为什么批准，Runtime 只消费 `CommandAuthorized` / `CommandRejected`。旧 `core/` 已删除，见 [新栈删除 Core 与越界审计](新栈删除Core与越界审计.md)。

对照时观察的不是功能是否更多，而是：中断是否自然、异步工具是否更稳、恢复是否更可信、Context 是否更好构造、Runtime 是否仍需懂业务、新能力是否更容易接、模型调用质量有没有因复杂状态下降。

## 方向二：上下文脱水优化

当前工具脱水保留原始事实，并通过 Artifact 提供回读路径；增量摘要则会生成新的上下文状态。链路在机制上可以持续执行，但反复压缩后的语义可靠性尚不清楚。

回补目标分为三层：

- 协议正确：压缩后消息结构与工具调用链仍然合法；
- 恢复正确：脱水内容可以通过 Artifact 引用准确回读；
- 任务正确：关键约束、事实、未完成状态和决策依据没有发生不可接受的漂移。

后续优化不能只比较 token 节省量或最终是否给出答案。应先利用可重放执行历史固定模型与工具事实，再比较不同脱水策略产生的上下文和行为差异。

“完美运行”暂不作为未经定义的结论，后续需要转换成明确、分层的可验证标准。

## 方向三：TodoList（新栈不迁）

旧 TodoList 已随 Turn `core/` 删除。新 Runtime 与新栈适配层不挂 `rewrite_todos`、不做 Todo 模式、不上 Sync Barrier。

依据见 [判定标准与 Judge 延后决策](判定标准与Judge延后决策.md)。

## 当前边界

- 暂不进入 Phase 7；先做接管前收口，再对照真实任务；
- 暂不实现 SubAgent、后台调度、Long Memory 或 Goal 新建模；
- 判定标准与独立 Judge 已在新栈 Host 实现，不把 Goal 聚合搬进 Runtime Core，见 [判定标准与 Judge 实现总结](判定标准与Judge实现总结.md)；
- 新栈 MCP 走 Host 侧 `load_toolset` 渐进加载，不把外部工具一次性塞进 Runtime，见 [新栈 Toolset 渐进加载与 MCP 接入](新栈Toolset渐进加载与MCP接入.md)；
- 新栈 Skill 是两个普通工具，不是新执行语义，见 [新栈 Skill 接入](新栈Skill接入.md)；
- Runtime 不再增加宏大能力；新栈投影保护窗、预算与 Artifact 已接上，见 [新栈 Model Context 投影实现总结](新栈ModelContext投影实现总结.md)；
- 新栈不引入 TodoList；旧 Turn `core/` 已删除，不迁移；
- 新栈 adapter 除 `legacy.py` 外不得 import `tools.*`；环境工具经该门装配。
- 默认入口是新栈 Runtime，见 [新栈删除 Core 与越界审计](新栈删除Core与越界审计.md)。
- 不为未来可能性提前建设通用分布式平台或新的规划抽象。
