# 架构总览

HelperMe 的运行事实在 Journal 里。模型看到的对话、人看到的一轮问答，都是投影。

> **Event 是唯一持久执行事实，State 是事件归约结果，Step 是决策推进单元，Command 是外部副作用闭环。**

完整决策见 [Runtime](Runtime.md)。

## 分层

```text
console_chat.py
      │
helperme/channels/                CLI / Telegram 输入、会话选择、控制命令
      │
helperme/assistant/               决策、上下文、完成判定、驱动、装配
      │
┌─────┴─────────────┬───────────────────────┐
│                   │                       │
helperme/runtime       helperme/llm + helperme/sandbox     helperme/mcp + helperme/skills + helperme/tools
执行内核            模型接口 + 执行环境                 MCP / Skill / 文件命令
```

当前 `SessionScheduler` 把已提交事实映射为同一事件循环中的异步激活，不规定不同 Session 的执行顺序；同一 Session 的 Step 保持线性提交。这个实现提供协作式并发，不提供执行资源隔离。多 Session 目前的唯一用途是 [SubAgent](SubAgent.md)：父 Agent 把只读调查委派给独立子 Session，结论经事实回灌。已确认但尚未实现的进程隔离方案见[多活跃会话](多活跃会话.md)。

| 包 | 职责 | 禁止 |
|---|---|---|
| `helperme/runtime` | Event、State、Step、Command、终态 Barrier | import 其他 helperme 模块 / host / plugins / tools |
| `helperme/assistant` | 模型决策、Context、Completion、Artifact、Session Scheduler、产品装配 | 控制台输入输出 |
| `helperme/channels` | CLI / IM 输入输出、会话 identity、投递幂等、控制命令 | 实现模型决策或 Runtime 推进循环 |
| `helperme/llm` | 模型契约、Provider 客户端与连接配置 | import Assistant / Runtime / Sandbox / MCP / Skills |
| `helperme/sandbox` | Workspace View、权限绑定、本地环境与进程执行 | import Assistant / Runtime / Tools / MCP / Skills |
| `helperme/mcp` | MCP Registry、Client、控制面 | 把 MCP 名词写入 Runtime；遮蔽第三方 `mcp` SDK |
| `helperme/skills` | Skill 包、安装、管理与两个普通工具 | 做成第三种执行循环 |
| `helperme/tools` | ToolSpec、参数契约、执行器、管理控制请求与环境工具 | 反向依赖 Assistant / Runtime / MCP / Skills；把控制请求当 Runtime 授权 |

测试统一通过 `python -m pytest` 运行；架构依赖边界由 `tests/architecture/test_import_boundaries.py` 强制验证，Runtime 行为由 `tests/runtime/` 的当前语义切片验证。`tests/live/` 默认跳过，只有显式设置 `HELPERME_RUN_LIVE_TESTS=1` 才调用真实模型。

当前按职责分片迁移，尚未为了目录整齐一次性搬动所有稳定模块。最终目录方向见[项目架构方向](../项目架构方向.md)。


## 一次推进

```text
UserMessageReceived
  → RUNNABLE
  → Step：模型决策 + 发出 Command
  → Dispatcher 执行工具（可并行）
  → CommandOutcomeReceived
  → 需要再决策则再开 Step
  → content-only deliver → WAITING(user_message)
```

工具还在跑或模型还在想时，后到的文本仍是 `UserMessageReceived`，不另建 Interrupt。Channel 即时入账；当前 Step 会提交，这一轮已签发的 Command 跑完后，由这条消息当下一拍 trigger，旧 Outcome 组不再单独要 Step。见 [Runtime 的“用户输入与后到消息”](Runtime.md#用户输入与后到消息)。

Channel Session 是持续对话生命线。一次回答结束后只进入 `WAITING(user_message)`；人在控制台继续打字，只是向同一 Session 追加下一条外部事实，不触发 `COMPLETED / TERMINATED`。当前 Channel 不装配 Completion Judge，也不请求 `finalize()`。

Runtime 保留 `COMPLETED / TERMINATED`，供未来明确有界的一次性后台执行显式使用；它们必须经过 Finalization Barrier。终态表示逻辑关闭，不负责持久数据回收。已实现的 [SubAgent](SubAgent.md) 不走这条路：子 Session 交回结论后停在 `WAITING`，一次性由投递幂等保证。

## 产品规则（判定）

人负责目标；模型补全判定标准；后一句默认改 inferred；只有人明确换事才改目标。详见 [判定](判定.md)。

## 入口

```text
python console_chat.py
```

Journal：`~/.helperme/runtime_sessions/journal.sqlite`。Toolset 激活由已提交的加载结果投影，Assistant ToolSurface 缓存可重建；`/new` 开新 Session，`/resume <session_id>` 选择已有 Session并在合法状态下唤醒。所有文本都是有序 `UserMessageReceived`；`Ctrl+C` / `Ctrl+D` 退出进程。

各外部入口选择 Session 与投递 identity 的规则见 [Channel 接入契约](Channel接入契约.md)。
