# 工作区版本

> 工作区的文件状态有版本，任何一步的改动都能退回去。**记录自动，回退显式。**

只解决文件。外部执行已经产生的副作用不可撤销，这里不假装能撤销。执行环境边界见 [Sandbox 与配置](Sandbox与配置.md)；多版本多分支空间的其余部分仍未设计，见[工作区](../未开始/工作区.md)。

## 为什么是这个形状

记录和回退的性质完全不同，这条分界决定了其余全部设计。

「刚才文件变成什么样了」是确定性的事实归约，没有语义可判断，因此在执行边界自动完成，模型不知道也不需要知道。「要不要退回去、退到哪一版」是语义判断，因此必须由模型显式发起。

由此得到两个推论，它们比上面那句更常被搞错。

**模型不需要任何工具去查版本。** 版本是 Journal 里的事实，上下文投影天然带着它，模型直接看得见上一步结束时是哪一版。所以这个能力对模型只新增**一个**回退入口，不把版本控制包装成一组查询与提交工具。

**回退不是时间倒流。** 它是一条新事实：把工作区恢复到某一版。Journal 只增不减，被撤销的那段历史照样在，后面多一条撤销记录——模型因此看得见自己反悔过，而不是醒来发现世界莫名其妙变了。回退本身也产生新版本，所以回退可以被回退。

## 不变量

**不碰用户的版本历史。** Agent 的版本轨道与用户自己的版本历史物理分离：独立的对象库指向同一份工作树，用户的引用、索引、暂存和工作树状态一个都不动。用户在这个目录里有自己的工作流，Agent 往里提交一次就足以破坏它。分离顺带买到一个好处——**工作区本身不必是版本仓库**，任何目录都能有版本轨道。

**回退不丢数据。** 回退前先强制记录一次当前状态。工作树上可能有还没被记录的改动，是用户手动改的，或是另一条会话刚写的；先记一次，它们也有了自己的版本，退得回来。于是恢复这个动作本身完全可逆。

**一个工作区一条轨道。** 文件世界只有一份。多条会话共享同一个工作区时，它们的版本交错在同一条轨道上——这是真实情况，如实记录，**不协调**。由此一条会话的回退会连带撤销另一条的改动；这和多条会话同时写同一个工作区是同一个问题，本来就是用户的选择，Agent 不替他兜底，见 [SubAgent · 只读边界](SubAgent.md#只读边界)。版本轨道让它从不可挽回变成可挽回，到此为止。

**没有记录就要说出来。** 记录失败是外部环境问题，不是契约违规，因此不阻塞推进——否则缺少后端的机器上 Agent 直接瘫掉。但**静默跳过比失败更糟**：那会让「可以反悔」无声失效，模型和人都以为还退得回去。所以失败要留下明确事实，让模型看见这一步没有版本记录。这与 `get_changes` 后端不可用时的既有立场一致：记录失败，不谎称无改动。

## 快照点是 Step 边界

不是每次写文件之后。直觉上的那个粒度有两处过不去：Dispatcher 会并行执行工具，两个写 Command 各自记录时，后一份必然含进前一份的改动，版本与 Command 的对应当场作废；而 `execute_command` 同样会改文件，它是否只读无法静态判断。

取「一个 Step 的全部 Command 结束之后记一次」，两个问题一起消失：只有一个记录点，没有竞态；不需要判断哪些工具会改文件，实际比较就知道。粒度也对齐了 Runtime 已有的批次概念——批次约束本就覆盖同一 Step 的工具调用组。

**内容无变化则不产生新版本**，沿用上一版。

代价是归因粒度变成「这一步做的全部改动」，而不是某一次工具调用做的改动。这不是损失：`get_changes` 本就明确不做变更归因，而要反悔的单位本就是一步。

## 版本是一条 Assistant 领域事实

照抄 MCP Toolset 的形状：成功的操作留下普通事实，其中记版本身份；恢复时从已提交事实投影；内存里那份只是可丢弃缓存，不是第二事实源。见[工具与能力](../能力/工具与能力.md)。

**不新增 Runtime Event，也不新增 Runtime State。** Runtime 不认识版本控制，就像它不认识 MCP。

Step 能携带的那份不透明决策元数据不是它的容器：元数据随 Step 提交，而记录发生在 Command 全部结束之后，那时 Step 早已提交。

## 谁来触发回退

**人的入口是说话，不是按钮。** 用户说「这版不行，退回改之前」，模型据此回退。按钮省下的只是一次模型调用，换来的是 UI、静止判断和一条人发起的外部事实入口；而且「退回我让你改登录页之前」对应哪一版，恰恰是该交给模型的语义判断，做成按钮反而要人自己干这件事。

更重要的触发方式是**模型中途自己反悔**：按一个方向改了几个文件、验证后发现不对，退回去换做法。这不需要任何界面，也是这个能力真正的收益所在。

Web 该做的不是撤销按钮，而是把版本事实显示出来，让人知道有东西可退。**时间线上的会话节点这个位置不占用**——编辑消息已经在那里，而它是 fork 不是回退，两者叠在同一个节点上必然被理解成「聊天和文件一起回到那时候」，那是尚未设计的分支语义。

## 记录范围

包含新建文件。Agent 建的文件必须能撤销，否则它留一地垃圾而你清不掉——这与 `get_changes` 的 diff 明确不含未跟踪内容**故意不同**。

尊重工作树自己的忽略规则，另外排除用户的版本目录。

已知限制：工作区没有忽略规则时，一次记录可能很大。如实承认，**不加护栏**。

## 分层落点

记录与恢复能力属于 `helperme/sandbox`，它是文件世界的所有者；「什么时候记录」属于 `helperme/assistant`，Step 边界是它的调度知识；`helperme/tools` 只放那一个回退入口。依赖禁令见[架构总览](../总览.md)。

## 不做

- 分支、合并、并行工作树（属于尚未设计的[工作区](../未开始/工作区.md)专题，现在碰就是预建状态机）
- 带 fork / merge 的工作区版本端口
- 向模型暴露提交、日志、比较工具（比较已经有 `get_changes`）
- 让 Runtime 认识版本，或为版本新增 Runtime Event / State
- 碰用户的版本历史、引用、索引与暂存
- 自动回退（「失败了就退回去」是语义判断，交给模型）
- 给子 Session 回退能力（只读白名单这轮不动）
- 把版本与 Journal 位置做成可双向导航的时间轴
