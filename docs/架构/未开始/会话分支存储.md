# 会话分支存储（未开始）

> 方向已定，设计未开始。本文只记要解决什么、会撞上哪些已有约束。

## 当前是什么

编辑消息以目标消息之前的完整事件前缀创建新 Session，见 [Web · 编辑消息是分支](../入口/Web.md)。物化是真抄一份：新 Journal 重放写入整段前缀，前缀引用的 Artifact 与附件一并复制。

这在编辑还是偶发动作时无所谓。「改写」成为默认动作之后它变成常用路径——一次对话里连改几次是常态，代价随历史长度线性增长，同一段历史在磁盘上躺着好几份。

## 会撞上的已有约束

这几条是现在明确成立的决策，改存储模型时必须正面处理，不能绕过：

- **Journal 是唯一持久事实源，事件不可重写。** 共享不能变成两条会话指向同一段可变数据——那样一条分支的追加会改写另一条的历史。见 [Runtime](../运行/Runtime.md)。
- **被顶掉的身份仍然是可打开的会话。** 会话线只列出头，但线上的历史身份不是坟墓，见 [Web](../入口/Web.md)。共享方案不能让它们退化成「要重建才看得到」。
- **Session identity 不是存储位置。** 现在两者恰好一一对应，一个 Session 一个目录一份 Journal。共享前缀会拆开这个巧合，凡是按目录找 Journal 的地方都要重新回答一次。
- **删一条分支不再等于删一个目录。** 现在根本没有删除入口，所以这个问题不存在；引入共享之前必须先回答删除语义，否则会攒出删不掉的东西。

## 待设计

共享的粒度（整段前缀还是按事件范围）、分支点怎么表达、重放时在哪儿拼接、删除与回收怎么定——全部未定。

在这些确定之前不预建 Journal 存储层抽象。现在只有一种存储形态，为想象中的第二种先开一个接口，是替不存在的问题加抽象。
