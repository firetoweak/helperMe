# 可写子会话（未开始）

> 方向已定，设计未开始。挡住它的是进程沙箱，不是工作区。

## 方向

让子 Session 能写文件、能执行命令，真正分担一段工作，而不是只能读和汇报。

## 当前是什么

子 Session 拿一份显式列举的只读工具名单，`execute_command` 永远不在其中。**只读不是保守选择，是当前唯一的安全边界**，见 [SubAgent · 只读边界](../运行/SubAgent.md#只读边界)。
    10|
## 挡路的是什么

Environment 向模型如实报告 `sandbox process="unavailable"`——本产品目前没有进程级隔离。父 Session 的写工具靠人授权兜住，子 Session 没有人在回路里：它是 Agent 自己造出来的并行，用户没参与，授权闸对它本来就不成立，见 [Command 授权](../入口/Command授权.md)。

所以顺序是先有进程沙箱，再谈写权限。[工作区版本](../运行/工作区版本.md)能收拾文件，但收拾不了 `execute_command` 的外部副作用，「反正能退」不构成放开的理由。

## 已经排除的做法

- **用工作区分支换写权限。** 给每个子一份隔离的文件空间只解决「互相踩文件」，不解决「这条命令会不会删掉家目录」。隔离文件和限制进程是两个问题，见[工作区](工作区.md)。
- **靠授权闸当安全边界。** 已经明确不成立，理由见上。
    20|- **按名字判断哪条命令只读。** 无法静态判断，这正是只读名单排除 `execute_command` 的原始理由。

## 待设计

进程沙箱用什么实现、跨平台覆盖到什么程度、拿不到隔离时是降级成只读还是拒绝启动、单写者不变量在多个可写子之间怎么维持——全部未定。

在这些确定之前不给只读名单开口子，也不做「受限的 `execute_command`」：一个能跑一部分命令的执行口，安全边界比现在的名单更难说清。
