# 长任务（未开始）

> 本文只记方向与已经排除的做法。方案确认前不按它实现，也不把它当成现行架构。

长任务有两个不同的问题，放在同一专题设计，但职责分开。

## 进度外化

解决遗忘和漂移：把待办事项、当前进度和阻塞原因写成可重放的事实，模型不必只靠上下文记忆任务全貌。

它和 [Compact](../上下文/Compact.md) 解决的不是一件事——压缩是在上下文塞不下时保留语义，进度外化是让任务全貌一开始就不依赖上下文。

## 完成核验

解决过早宣布完成：模型声称完成时，系统先检查是否存在必要的客观证据，例如实际工作区变更和验证结果。

**证据是否满足用户目标仍是语义判断**，应交给模型、独立 Judge 或用户，运行内核不替他们作结论。

### 现状与缺陷

当前靠 tools-loop 判定：看模型返回里还有没有 tool call，以此决定是否继续推进。

缺陷在长任务上暴露：模型的输出经过多轮对话后可能已经偏离最初的 task，"没有下一步动作"不等于"任务完成"。要补的是外部审计与执行状态检测，而不是把这套隐式判定做得更复杂。

上层还有一个相关问题：对话稍长后模型可能忘记主动核验工作区变更，误以为修改已经完成。这属于完成核验，**不通过扩张 `get_changes` 解决**——那个工具只回答"工作区实际发生了什么"，见[工具与能力](../能力/工具与能力.md)。

## 已经排除的做法

- **定时唤醒不作为长任务方案。** 缺少新事实的任务不会因为被定时叫醒就变得更可靠。
- 现有简单任务继续自然运行：工具结果触发下一步决策，模型没有下一步动作时回到等待用户输入。不为长任务改这条通路。
- 方案确认前，不接通声明式完成，也不增加独立 Judge。
- 不向 Runtime 增加 Goal / Criteria 状态，也不从 Host 内存向 Decision Context 注入可变判定标准。未来引入 Judge 时先定义 Journal 事实、identity 与所有者。
