# 工作区（未开始）

> 方向已定，设计未开始。本文只记要解决什么、会撞上哪些已有约束。

## 方向

把工作区升级成**多分支空间**：不再只是"磁盘上的一个目录"加一条线性版本轨道，而是能开分支、能并行存在多个版本、能比较和取舍的空间。

## 当前是什么

现在的工作区是一份扁平清单加一条会话级绑定：一条会话只属于一个工作区，Worker 装配时按该绑定读取根集合，可选挂上 Host 根。边界见 [Sandbox 与配置](../运行/Sandbox与配置.md)，进程侧见[多活跃会话](../运行/多活跃会话.md)。

文件状态已经有版本可退，见[工作区版本](../运行/工作区版本.md)；但那条轨道是线性的，没有分支。工作区也还没有专属准绳——其余约束分散在 Sandbox、多活跃会话和 [Web](../入口/Web.md) 三处。这次升级顺带把它们收拢到本文件夹。

## 升级会撞上的已有约束

这几条是现在明确成立的决策，改工作区模型时必须正面处理，不能绕过：

- **跨 Session 写冲突不由 Agent 协调。** 多个顶层 Session 对同一 Workspace 的写入来自用户选择，Agent 不替他兜底。分支如果能消除一部分冲突，那是分支带来的收益，不是把协调职责搬回 Agent 的理由。见 [SubAgent · 只读边界](../运行/SubAgent.md#只读边界)。
- **`get_changes` 只报工作区快照，明确不做变更归因。** 引入分支后"和谁比"会变成一个真问题，但答案应该是让调用方指定基线，而不是让工具去猜是谁改的。见[工具与能力](../能力/工具与能力.md)。
- **会话 fork 不 fork 工作区，但已经不再回避文件。** 编辑消息切分支时由人选文件退不退，选不退要留一条事实告诉模型磁盘上有本分支历史看不到的改动，见[工作区版本 · 触发](../运行/工作区版本.md#触发)。那是一个文件世界下的诚实处理，不是分支：两条会话线仍然共用同一份工作树，谁动了文件另一条立刻看见。**会话分支要不要对齐成工作区分支，仍是本专题要回答的问题。** 见 [Web](../入口/Web.md)。
- **Agent 不拥有工作目录。** Environment 描述"在哪里执行"，由调用方每次指定。多版本空间不能变成"Agent 记着自己现在在哪个分支"的隐藏状态。

## 待设计

分支的身份怎么定、和 Session identity 是什么关系、切换分支算不算一条需要进 Journal 的事实、沙箱边界随分支怎么移动——全部未定。线性版本已经答了「版本是一条 Assistant 领域事实」，分支不能默认沿用这个答案：一条线上追加和多条线并存不是同一个问题。

在这些确定之前不预建工作区状态机，也不把 git 命令包装成一组新的 Function Tool（那会和 [CLI 能力](../能力/CLI能力.md)的"执行空间"端口重复）。已落地的回退是**单独一个**入口、且不暴露查询与提交，不属于被排除的那一组。

**给子会话开写权限不算本专题的收益。** 隔离文件解决不了「这条命令会做什么」，挡在那件事前面的是进程沙箱，见[可写子会话](可写子会话.md)。拿它当分支的理由会把两个问题搅在一起。
