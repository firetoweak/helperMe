# 多模态附件

> 状态：工具回图与 TUI 用户粘贴均已落地。音频不在本设计范围内。

工具带回的图片字节不进 Journal，只进 Session 目录；Journal 持有内容寻址引用；投影器按引用还原为模型内容块；Client 在请求边界读字节。Runtime 全程不认识 mime、不认识图片：工具回图走 `CommandOutcomeReceived.outcome.value` 的不透明 JSON；用户粘贴是一条普通用户消息，稳定 id 放进已有的 `event.artifact_refs`。

## 为什么必须外置

`helperme/runtime/model.py` 的 `MAX_JSON_VALUE_BYTES = 128 * 1024` 是所有事实值的硬上限，`CommandOutcome.__post_init__` 对 `value` 调 `freeze_value` 时逐字节扣减预算。一张 1280×720 截图 base64 之后是兆级，**写不进 Journal，会在事件构造时抛 `JSON value exceeds maximum size`**。

所以外置不是体积优化，是唯一可行路径。这与超长文本结果被同一上限逼出 Artifact 外置是同一个成因。

## 两类外置物

| | 文本 Artifact | 附件 |
|---|---|---|
| 成因 | 单条结果超过字符阈值 | 二进制天然不可进 Journal |
| 标识 | `art_<32hex>`，每次外置新建 | `sha256:<hex>`，内容地址 |
| 读取 | 按字符 offset 分页 | 整件取回，不可分页 |
| 位置 | `<session>/artifacts/` | `<session>/.attachments/` |
| 工具 | `read_artifact` | `read_image` |

两者都在 Session 目录下、都是 execute-time 产生的事实、丢失都算持久化损坏。但 API 语义相反：文本可连续降级，图片只有「在」与「不在」两态。**不得把附件并入 Artifact Store，也不得为二者预建统一 blob 抽象。**

投影器 `_dehydrate` 造的那批 Artifact 是另一回事：它是投影期缓存，用随机 id，重放会重新生成，不进 Journal。附件与之无关。

## 存储

```text
~/.helperme/runtime_sessions/<session-key>/
  journal.sqlite
  artifacts/            文本溢出、Replay Manifest
  .attachments/<id>     图片字节
```

按内容哈希寻址：相同字节得到相同 id，只存一份。截图循环里页面未变即复用，崩溃重试产生相同字节也不会重复落盘。

写入是「暂存文件 + `replace()`」：内容寻址靠文件存在与否判重，若直接写规范路径，崩在写一半会留下截断对象并被永久当成有效。这是单个对象的标准原子写，不是多文件事务。

**不使用 sidecar 元数据文件**，mime 与尺寸跟随引用对象进入事实，磁盘上只有裸字节。硬链接去重、逐级目录 fsync 之类的耐久性工程不做——本项目一个用户，不为不存在的问题建工程。

附件缺失是持久化损坏，读取时原样暴露，不降级成「没图」。保留策略与垃圾回收本版不做；孤儿对象（字节已落盘而 Outcome 未提交）是垃圾，不是错误。

## 准入

只接受 PNG、JPEG、WebP、GIF。其余 mime 在 MCP 边界**拒绝**，返回语义明确的错误，不落盘。

理由：下游本来就是封闭的——附件最终要走 provider 的图片协议，provider 只认有限几种格式。存一个 SVG 下来，投影时照样发不出去，只是把「不可用」从入口推迟到投影，那时报错离现场更远。

落盘前完整解码栅格，声明 mime 与实际格式不符则拒绝。超过归一化上限的图做确定性重编码后再存，**磁盘上是归一化后的字节**，引用里同时记录原始事实与归一化事实。

把输入压到有界，比为无界输入精确建模成本要简单，也顺带消除了 provider 尺寸限制导致的请求失败。上限以模块常量固化，出现真实需要时再提升为配置。

## 引用形状与工具结果协议

```json
{"type": "image", "id": "sha256:…", "mime": "image/png", "width": 1280, "height": 720}
```

模型侧工具结果协议由 `{ok, code, data, error, hint}` 扩展出**可选第六键 `images`**，值为引用列表；同时 `data` 内对应的原始图片块替换为同一引用对象。

`images` 放在顶层而不是塞进 `data`，因为它是投影指令而非工具载荷：投影器要在不理解任何具体工具的前提下找到它，并且它必须在正文被外置成 Artifact 之后继续存活——外置 stub 保留 `images`。

## 顺序约束

**抽图 → 引用替换 → 文本外置 → 构造 Outcome。**

顺序反了，`externalize_tool_result` 会把带 base64 的结果当作普通长文本计入字符阈值，把兆级 base64 文本写进一个 `art_*.json`：既没解决问题，又污染了文本抽屉。

另：MCP 适配器对文本做密钥脱敏时**必须跳过二进制块**，字符串替换会破坏原始字节。

## 投影

图片块不能放进 `tool` 消息——Chat Completions 的 tool 消息只接受文本。因此图片跟在**完整工具响应组之后**，作为单独一条 `user` 消息注入，并在文本里标明「这是工具观察，不是用户指令」。tool 消息本身保持既有文本协议不变。

投影版本升至 3。

用户粘贴仍是一条普通用户消息。Channel 先把字节写入当前 Session 抽屉，`content` 带可见 token（例如 `[Image #1]`），稳定 id 写入 `event.artifact_refs`。投影器按 id 从抽屉嗅探 mime 与尺寸，还原为与工具图相同的内容块。消息因此始终非空；`yes` / `no` 授权只看纯文本，带着 token 的正文不会被当成确认。

## 预算与驱逐

图片按件计入预算，**不对引用做文本分词，也不对 base64 分词**；初值取每件 1600 token，由真实 usage 校准。

图片另有一份 token 预算，超出时**从最旧的开始脱水**为文字引用，并提示可用 `read_image` 回读。

不写「只保留最近 N 张截图」。那条规则隐含「新截图让旧截图失效」的语义判断，而有些场景旧图恰是基准——按原则 4，这属于模型的地界。纯资源驱逐与既有的保护窗、体积外置同族，不新增任何关于图片含义的假设；模型认为旧图仍需要，自己回读。

## 回读

`read_image(id)` 只接受**本 Session 事实中出现过的** id，整件取回。不提供分页——图片不可分割。规则与 `read_artifact` 同类：按本 Session 引用取回，不新开执行循环。

压缩 handoff 只保留 id 与来源；来源由持有引用的事件类型直接读出，不另存。摘要文字不等于看过原件，业务模型要再看走回读。

## 请求边界

上层消息协议自始至终保持本地引用。Client 只在构造 provider 请求时读字节、转协议，**同一请求内相同 id 只编码一次**，不回写 Journal，不持久化 base64。

同一张图留在可见窗口期间，每一轮都会重新编码上传，这是 token 之外的第二笔成本；内容寻址让「本轮与上轮是同一张图」退化为一次 id 比较，为后续复用上传留出空间。

## 不做

- **不改 Runtime payload / codec**：不加事件类型、不升版本、不碰空消息不变量。`_append_external` 只把已有的 `artifact_refs` 入口接出去。
- **附件不进 Workspace**：Workspace 是变更证据的对象，附件落在那里会出现在 `get_changes`、弄脏工作区、甚至进 git。
- **不做保留与 GC**：孤儿与历史对象暂时积累。
- **不设计音频**：到来时复用外置 + 引用 + 投影这条路，只加存储格式、投影块和一条窄回读工具。
- **不做 SubAgent 继承**：子 Session 是独立 identity，`read_image` 按本 Session 取回意味着看不到父 Session 的图。是否照文本 Artifact 的 bundle 继承机制处理，待真实需要出现时单独决定。
