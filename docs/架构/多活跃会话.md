# 多活跃会话

> 状态：已实现。Host Supervisor 管理独立 Session Worker；每个 Worker 内的 `SessionScheduler` 只推进自己的 Session。

## 决策

Session 是执行隔离单元，也是持久化隔离单元。每个活跃 Session 在独立操作系统进程中装配一套完整实例：Runtime、事件循环、模型客户端、工具与 MCP 客户端、Session 投影缓存，以及只属于它的 Journal。一个 Worker 不承载第二条 Session。

```text
Channel / SubAgent 回传
          │
          ▼
Host Supervisor
  ├─ Session A Worker ─ Runtime ─ Journal A
  ├─ Session B Worker ─ Runtime ─ Journal B
  └─ Session C Worker ─ Runtime ─ Journal C
```

非活跃 Session 不占用进程。新事实到达或用户执行 `/resume` 时，Host 启动对应 Worker；Session 再次静止或进入终态后，Worker 退出，Journal 保留生命线；只读 SubAgent 的中断回退是下述明确例外。

进程边界保证一个 Session 内的同步阻塞、事件循环停顿和未预期异常不会暂停其他 Session。Session 内部仍按 Runtime 契约推进：Step 线性提交，同一 Step 的 Command 可以并行执行。这次改造不把每次工具调用再拆成独立进程。

## Host 与 Worker

Host Supervisor 只负责机械职责：

- 根据给定 Session identity 定位持久目录；
- 保证本机同一时刻至多启动一个对应 Worker；
- 把外部事实、授权决定和唤醒请求送到 Worker；
- 接收输出、静止、终态和进程失败信号；
- 在父子 Session 之间路由带稳定 delivery identity 的回传事实。

Host 不读取事实含义，不归约 Runtime State，也不决定任务是否完成。可否继续推进、一次 Step 看见哪些事实、Command 是否已经终结，仍由目标 Session 的 Runtime 和 Journal 决定。

Worker 启动后只处理一个 Session：打开它的 Journal，重建 Runtime 与 Assistant 投影，接纳本次请求并推进到静止。存在未结束的模型调用、Command 或待用户确认的管理提案时，Worker 保持存活。管理提案仍沿用现有进程内控制面，在确认前不能随静止退出。未预期异常直接结束 Worker 并由 Host 暴露；Host 不把它转换为普通失败。恢复时，当前只读 SubAgent 按下述回退规则处理未完成 Attempt；其他 Session 不自动重试已经开始但没有 Outcome 的 Attempt。

IPC 只承载应用请求和生命周期信号，不复制 Runtime 内部状态。事实必须先由目标 Worker 可靠写入自己的 Journal，Host 才能确认投递成功。

边界上的出入口保持窄而明确：Host 向 Worker 发送新建、投递、授权或无新事实的恢复唤醒；Worker 向 Host 返回投递已接纳、对外输出、静止、终态或失败。失败信号保留异常类型、消息和 traceback，不把异常改写成 Runtime Outcome。Worker 启动中或退出中到达的投递由 Host 等待该次状态转换后送入同一个 Session，未写入 Journal 前不向调用方确认。

## 每 Session 一个 Journal

持久布局改为：

```text
~/.helperme/runtime_sessions/
  <session-key>/
    journal.sqlite
```

`session-key` 是 Session identity 的稳定、文件系统安全映射；Journal 内仍保存并校验原始 identity。目录存在即表示这条 Session 生命线存在，不另建全局 Journal 或第二份事实目录。

每个 Journal 只保存一条 Session，因而不同 Session 不再竞争同一个 SQLite 写锁，Checkpoint、claim 和恢复也不会扫描无关会话。配置、Skill、MCP Registry 和用户指定的 Workspace 仍是产品级资源；Worker 在装配边界读取它们。多个顶层 Session 对同一 Workspace 的写入来自用户选择，不由 Agent 增加跨 Session 协调。

## 父子 Session

SubAgent 仍是普通 Session，使用相同的 Worker 和 Journal 边界。父子关系继续由 Assistant 事实表达，不进入 Runtime State。

```text
父提交 delegate Command
  → Host 创建并启动子 Session
  → delegate Outcome 只确认子 Session 已建立
  → 父静止，父 Worker 可以退出
  → 子静止并形成 report
  → Host 启动父 Worker（如果尚未运行）
  → 父 Worker 将 subagent.report 可靠写入父 Journal
  → 父 Worker 继续推进
```

父进程不等待或持有子进程。结论是否收齐仍由父模型根据已提交事实判断；Host 只用稳定 delivery identity 保证每个子结论最多回收一次。子 Session 的只读工具边界保持不变。

子回传内容先以 `subagent.return` 保存在子 Journal，再通过 Host 投递到父 Journal。恢复子 Session 时重投同一份内容；父按稳定 delivery identity 去重。恢复父 Session 时，Assistant 从已提交的委派与回收事实找出未回收的子 Session，分别请求恢复；不会扫描无关 Session。

## 租约与接管

租约用于 Worker 崩溃后的接管，不把正常但暂时停顿的 owner 判成失败：

- 到期只表示新的 Worker 可以竞争接管；
- 成功接管必须产生更高的 `generation`；
- 续租和提交以 `token + owner_id + generation` 的当前身份为准；
- 没有发生接管时，原 Worker 在到期后恢复，仍可续租或提交；
- 原 Worker 提交与新 Worker 接管由同一 Journal 事务决定先后，只有一个能够成为有效写入者。

除下述只读 SubAgent 的明确例外外，Attempt 已经开始而 Worker 在 Outcome 入账前退出时，仍保持 `unknown`。时间经过本身不能制造 `unknown`，恢复也不能据此盲目重试外部副作用。

### 已确认取舍：只读 SubAgent 回退重试

当前所有 SubAgent 都只有读权限，没有写权限。恢复时，对“Attempt 已开始、Outcome 未入账”的操作，直接删除该未完成 Attempt 的持久记录，使对应 Command 回到 Attempt 开始前的可执行状态，然后重新执行。删除后不重排、不复用事件序号，并清除 Checkpoint，在重建任何投影前完成回退。已经提交的决策、其他 Command 的记录和已入账的 Outcome 保留。

这是已知且有意保留的系统缺陷：被删除的 Attempt 不再可追溯，Journal 不保留完整执行历史。这明确例外于 Event 不可修改和未知 Attempt 不自动重试的通用契约。该决策已实现；设计依据仅为当前 SubAgent 的只读权限，不为尚未设计的写权限子 Agent 增加重试契约或抽象。

## 生命周期

Host 只维护瞬时的进程状态：未运行、启动中、运行中和停止中。Session 的 `RUNNABLE / WAITING / COMPLETED / TERMINATED` 仍由 Journal 归约，不能用进程是否存在代替。

- 新建：原子建立 Session 目录和 Journal，再启动 Worker 接纳首条事实。
- 唤醒：Worker 已运行则投递给它；没有运行则启动同一 Session 的新 Worker。
- 静止：Worker 报告归约后的静止状态并退出。
- 崩溃：Host 移除进程记录并暴露原始失败，Journal 保持崩溃前的事实。子 Session 的未知异常（含配置、装配和客户端初始化失败）在 Worker 退出前先写入 `subagent.return`，单向通知 Host 负责投递 `subagent.report`，并暴露原始 `ProcessFailure`；Worker 不等待投递回复，Host 先释放死掉的 Worker，再完成回传；这不是把异常改写成 Runtime Outcome，也不自动重试。进程被直接杀掉、没走到这段回收时，父侧待回收集合仍在，要显式 `/resume` 才按下面的规则重建。
- 恢复：Host 重启后只恢复显式选中的 Session，不扫描并自动恢复全部历史 Session。`/resume` 启动目标 Worker，由它从自己的 Journal 重建；已有 `subagent.return` 只重投，不重新执行。当前只读 SubAgent 的未完成 Attempt 按上述规则删除并回退重试，其他 Session 仍按现有未知 Attempt 恢复契约处理。

Worker 退出采用静止通知与停止确认：Host 有尚未确认的应用请求时不会批准停止；Worker 确认期间若又有活动，会拒绝停止。Windows 下 Worker 纳入 Host 持有的 Job Object，Host 退出时其 Worker 一起结束，避免重启后遗留旧写入者。

异常回传不要求完整 Assistant 已装配。新建子 Session 时，`subagent.task` 与 Journal 一起原子建立，保证首次初始化失败也能找回父身份。持久化完成即确认创建，由 Host 异步启动子 Worker；子初始化失败不会卡住父的 delegate Attempt，而是经 report 回传。Journal 无法读取或写入时不伪造回传事实；回传本身再失败则同时保留原异常与回传异常。

## 实现位置

- `helperme/assistant/supervisor.py`：进程生命周期、投递与失败通知。
- `helperme/assistant/worker.py`：单 Session 装配、应用请求与静止退出。
- `helperme/assistant/ipc.py`：进程间应用请求和生命周期信号。
- `helperme/assistant/session_store.py`：identity 映射与新 Journal 原子建立。
- `helperme/runtime/journal/sqlite.py`：租约事务与恢复前回退。

## 不负责

- 协调用户主动创建的多个顶层 Session 对同一 Workspace 的写入；
- 隔离操作系统、磁盘、网络或外部服务自身的容量限制；
- 让多个 Host 或多台机器共同竞争同一条 Session；
- 为旧的全局 Journal 保留双轨、fallback 或长期兼容层。

## 验收

改造完成至少需要证明：

- Session A 的事件循环阻塞超过租约时间时，Session B 仍能继续决策和调用工具；
- 多个 SubAgent 同时活跃时各自在独立进程和独立 Journal 中推进；
- 父 Worker 已退出时，子 report 仍能可靠投递并重新唤醒父 Session；
- 一个 Worker 未预期崩溃不会停止其他 Worker；子 Session 的未知异常持久化后由 Host 回传 `subagent.report`，并独立暴露原始失败；当前只读 SubAgent 恢复时删除未完成 Attempt 并重新执行，保留其他已提交事实；其他 Session 的未知 Attempt 不被自动重试；
- 没有新 generation 接管时，租约到期的原 Worker 仍能提交；发生接管后，旧 generation 必须被拒绝；
- `/resume` 只打开和重建目标 Session，不依赖全局 Session Journal。
