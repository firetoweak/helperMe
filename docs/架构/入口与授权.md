# 入口与授权

各类 IM Channel 共用的 identity、投递幂等、并发输入与输出路由约束见 [Channel 接入契约](Channel接入契约.md)。本页记录当前 TUI 与 Telegram 的具体入口行为。

## 入口

```text
python console_chat.py
python console_chat.py --workspace <path>
```

`--workspace` 显式登记或复用该路径；缺省使用启动目录。TUI 每次启动生成新的 Session，并绑到这个工作区。

控制台启动只打印用法。TUI 始终由单个后台 Prompt 任务独占标准输入，并把完整行送入输入队列；`你：` 在空闲和运行期间都可编辑。运行期间队列中的新行仍是 `UserMessageReceived`，不是 Interrupt；它如何改写下一拍决策见 [Runtime 的“用户输入与后到消息”](Runtime.md#用户输入与后到消息)。所有后台输出由同一终端呈现层写到编辑行上方，再恢复输入内容与光标；模型正文 delta 直接续写同一次输出，提交后的 `deliver` 只结束该行，不重复全文，异常结束则标出中止。Agent 执行不直接操作键盘或编辑行。底部工具栏显示当前模型输入上下文占用；请求前使用投影后的估算值，响应后切换为 LLM 返回的实际 input usage，分母使用配置的模型 context limit。同一栏展示 compact 次数与相位（整理中 / 等待切换 / 失败）。`●` / `○` 单独成行。两次用户输入之间画一条横线，不按 Step 切。Journal、Step、授权事实、判定和渐进加载的说明在本页与其他架构文档，不进启动横幅。

只走新栈。TUI 的输入读取与 Agent 推进并行：每条文本都由 Channel 单次接纳为 `UserMessageReceived` 并唤醒 Session。当前 Step 使用冻结视图完成。运行中新行与空闲输入是同一条路径；后到消息如何改写下一拍决策，见 [Runtime 的“用户输入与后到消息”](Runtime.md#用户输入与后到消息)。Channel 不维护运行中输入的特殊协议。

TUI 每次启动生成新的 Session identity，持久创建后通过 `select(owner, identity)` 将它设为当前 Session；`/new` 也执行同样流程，仍落在启动时登记的那个工作区。`/resume <session_id>` 只选择用户明确指定且已持久创建的 Session，包括尚无 Event 的空 Session，不猜测“最近一个”。选择成功后 Host 才替换该 owner 的旧映射；失败时旧选择不变。Assistant 应用服务重建投影并在 State 合法可运行时唤醒 Session，Channel 关闭时释放 owner。

TUI 与 Telegram 的 Session 都是持续对话生命线，没有绝对终态；一次回答完成后回到 `WAITING(user_message)`。运行中和空闲时的新文本采用同一条 UserMessage 路径。

`Ctrl+C` 和 `Ctrl+D` 都是进程级退出，不写 Runtime Event。

Telegram Channel 使用 `channels.telegram.allowed_chat_id` 作为入口访问边界。该值为 `null` 时只启动配对模式：`/start` 仅在 Telegram 回复和本地控制台展示来源 `chat_id`，不装配 Assistant、不创建 Session、不接收任务。正常模式以 Telegram `bot_id + chat_id` 作为对话 identity；token 只是凭证，不参与 identity。工作区只接受 `--workspace`；没给时回退到最近一次聊天的工作区，完全没有则报错退出，不从进程启动目录隐式登记。所有文本按 update delivery 顺序接纳为 UserMessage。模型首个正文 delta 创建消息，后续 delta 以 0.5 秒窗口合并编辑；最终 `deliver` 刷新为已提交正文，明确的临时网络、服务端和限流错误在 Channel 内重试。

TUI 只处理能够确认来源的输入错误和控制信号。内部契约违规或未预期异常必须穿透 Assistant 与 Channel，在进程入口直接暴露，不能打印后继续运行，也不能降级成业务失败。

模型重试、冷却与路由策略由进程内 LiteLLM Router 决定；重试次数与单次尝试超时不写进用户配置，由代码默认注入（`DEFAULT_ROUTER_SETTINGS`：3 次 / 60 秒）。Adapter 只转换认证权限、上下文超限、连接超时、限流、Provider 5xx 等已有明确语义的错误。模型错误最终逃逸后台 Step 后，Scheduler 立即唤醒 Channel 的失败等待；TUI 或 Telegram 展示已识别的模型错误并停止当前进程，未知异常保持原样穿透。失败的模型决策没有提交 Step，Session 仍保留为可恢复的 `RUNNABLE`，修复配置并重启后可显式 `/resume`，但原进程不会继续显示为运行中。

若 Tool 异常逃逸，已经持久开始但没有 Outcome 的 Attempt 保持 `unknown`，当前进程不会捕获异常后自动继续。用户明确 `/resume` 只重建投影和唤醒合法 `RUNNABLE` State，不重试或伪造未知副作用的结果。

| 输入 | 事实 |
|---|---|
| 普通句子 | `UserMessageReceived` |
| 任意普通文本 | 外部 `UserMessageReceived` → wake Session |
| `/new` | Channel 生成 identity，Assistant 交给 Runtime 创建新 Session |
| `/resume <session_id>` | Channel 选择已有 Session；Assistant 重建能力并按当前 State 唤醒 |
| `/mcp` `/skill` | TUI 控制面，不进 Journal 当用户任务 |
| 待授权时的 yes / no | `CommandAuthorized` / `CommandRejected` |
| 待授权时的其他句子 | 仍是 `UserMessage`，下一步模型判断 |

## 两条边界

**副作用安全**：产品装配的 Tool Spec / Binding 显式声明 `requires_authorization`，签发 Command 时冻结该要求。需要授权的 Command 没有 `CommandAuthorized` 就不能 dispatch；模型不能批准自己。Runtime 不根据工具名、参数或模型措辞推断风险。

**意图**：这句话是什么意思，由下一步 Step 判断。Runtime / Assistant 不得因为“正在等授权”就丢掉用户话。

yes / no 在等待授权时由 Channel 映射为授权事实，因为那是人在回答产品的批准问题，不是模型该投的票。

MCP/Skill/CLI 安装与恢复使用 `helperme.tools.control.ControlApprovalRequest`，属于 Host 管理控制面；它不会写成 Runtime Command 授权，也不能让普通工具结果进入授权等待态。模型可以在普通对话中调用独占的 `propose_*` 控制工具。Assistant 只暂存已校验参数，待 Step 成功提交后才准备冻结方案；Channel 从 Journal 投影待裁决项，并把后续 `yes/no` 交给对应 Application Handler。

写文件类内置工具（`write_file` / `apply_patch` / `replace_all`）声明 `requires_authorization=True`。Web 用 Session 总闸决定要不要逐次确认；TUI 没有这把闸，入口上拦截 `ask`，用 yes/no 一次性处理当前全部待授权命令。这只是产品装配当前声明，不是 Runtime 的内置白名单。以后调整某个工具的策略只改其 Spec / Binding，已签发 Command 的授权要求不会随配置变化。见 [Command 授权](Command授权.md)。

## 安装

安装、恢复、更新、删除或启用 MCP / Skill / CLI 有两种入口：直接使用 `/mcp`、`/skill`，或在普通对话中先按需加载对应管理域，再由模型提交 `propose_*`。管理域成功加载后，诊断与提案 Schema 从下一 Step 才可见。提案必须单独调用；用户确认前不执行变更。MCP 对话删除走 `propose_mcp_remove`；TUI 仍可直接 `/mcp remove`。

## 控制提案

控制面不进 Runtime Command。待裁决提案只有一份事实，在 Journal 里：出现 `assistant.control.proposed`、其后没有 `assistant.control.resolved`，就是待确认。Host 只读投影与 Worker 决策各自重放同一段事件，进程之间不传这份状态，也不留镜像。一次 `decide()` 内部的 `_staged` 仍只活在 Worker 内存里，它只有一个读者。

提案 handler 在 Step 提交之后跑，可能探测外部世界。三种结局都先成为事实，再决定要不要继续决策：

| fact_type | 何时 | `requests_decision` |
|---|---|---|
| `assistant.control.proposed` | handler 返回待确认请求 | 否，停下等人 |
| `assistant.control.concluded` | handler 返回已知结论（dict） | 是 |
| `assistant.control.failed` | handler 抛出异常 | 是 |
| `assistant.control.resolved` | 用户确认或取消之后 | 是 |

`proposed` 与 `resolved` 的 delivery 身份是 `{request_id}:proposed` / `{request_id}:resolved`，避免撞到 Journal 的 `(source, delivery_id)` 唯一键。`failed` / `concluded` 用 Step 的 trigger 与 cursor 做 delivery 身份，同一 Step 重试不会写两条。提案失败把异常类型、消息和 traceback 写进事实，不再把探测失败当成 Worker 进程故障。

裁决结果仍交给 Application Handler 执行。执行已经改了世界的一半却中途失败时，仍先写下 `resolved`（`succeeded=false`），重试不会再执行一次。

Channel 从投影出示 `summary` / `risk`：Web 用确认框，TUI / Telegram / ACP 读 `control_approval`。提案本身不走 `deliver`，不进对话时间线。`proposed` / `concluded` / `failed` 只写事实；`deliver` 的 `output_id` 只能是该 Step 的 trigger event id，禁止另造投递身份。用户确认后的执行说明走 `control_message`，并与 `resolved` 事实同一份内容。有待裁决项时不再向模型提供控制工具 Schema。

进程退出或 Worker 静止不再丢掉待确认项；恢复后从 Journal 重新投影，绝不自动执行。过期确认（Session 已无待裁决项）仍会按内部异常穿透 Worker，跨进程的已知错误回传还没做。

## 持久

每个 Session 使用独立 Journal：`~/.helperme/runtime_sessions/<session-key>/journal.sqlite`，其中 `session-key` 是 Session identity 的稳定、文件系统安全映射。不兼容旧全局 Journal。详见[多活跃会话](多活跃会话.md)。测试可使用 `MemoryJournal`。
