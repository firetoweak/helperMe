# 入口与授权

各类 IM Channel 共用的 identity、投递幂等、并发打断与输出路由约束见 [Channel 接入契约](Channel接入契约.md)。本页记录当前 CLI 与 Telegram 的具体入口行为。

## 入口

```text
python console_chat.py
```

控制台启动只打印用法。CLI 始终由单个后台 Prompt 任务独占标准输入，并把完整行送入输入队列；`你：` 在空闲和运行期间都可编辑，队列中的新行在运行期间成为打断。所有后台输出由同一终端呈现层写到编辑行上方，再恢复输入内容与光标；Agent 执行不直接操作键盘或编辑行。底部工具栏显示当前模型输入上下文占用；请求前使用投影后的估算值，响应后切换为 LLM 返回的实际 input usage，分母使用配置的模型 context limit。`●` / `○` 单独成行。两次用户输入之间画一条横线，不按 Step 切。Journal、Step、授权事实、判定和渐进加载的说明在本页与其他架构文档，不进启动横幅。

只走新栈。CLI 的输入读取与 Agent 推进并行：每条文本都由 Channel 单次接纳为 `UserMessageReceived` 并唤醒 Session。当前 Step 使用冻结视图完成，新文本按 Journal 顺序开启后续 Step；Channel 不维护运行中输入的特殊协议。

CLI 每次启动生成新的 Session identity，并把它交给 `AssistantSessions.create(identity)`；`/new` 也执行同样流程。`/resume <session_id>` 只打开用户明确指定且已持久创建的 Session，包括尚无 Event 的空 Session，不猜测“最近一个”。Channel 负责选择 identity；Assistant 应用服务重建 Host 投影并在 State 合法可运行时唤醒 Session。

CLI 与 Telegram 的 Session 都是持续对话生命线。Channel 不装配 Completion Judge，不调用 `finalize()`；一次回答完成后回到 `WAITING(user_message)`。运行中和空闲时的新文本采用同一条 UserMessage 路径。Channel 不提供 `/stop`。

`Ctrl+C` 和 `Ctrl+D` 都是进程级退出，不写 Runtime Event。

Telegram Channel 使用 `channels.telegram.allowed_chat_id` 作为入口访问边界。该值为 `null` 时只启动配对模式：`/start` 仅在 Telegram 回复和本地控制台展示来源 `chat_id`，不装配 Assistant、不创建 Session、不接收任务。正常模式以 Telegram `bot_id + chat_id` 作为对话 identity；token 只是凭证，不参与 identity。所有文本按 update delivery 顺序接纳为 UserMessage。

CLI 只处理能够确认来源的输入错误和控制信号。内部契约违规或未预期异常必须穿透 Assistant 与 Channel，在进程入口直接暴露，不能打印后继续运行，也不能降级成业务失败。

若 Tool 异常逃逸，已经持久开始但没有 Outcome 的 Attempt 保持 `unknown`，当前进程不会捕获异常后自动继续。用户明确 `/resume` 只重建投影和唤醒合法 `RUNNABLE` State，不重试或伪造未知副作用的结果。

| 输入 | 事实 |
|---|---|
| 普通句子 | `UserMessageReceived` |
| 任意普通文本 | 外部 `UserMessageReceived` → wake Session |
| `/new` | Channel 生成 identity，Assistant 交给 Runtime 创建新 Session |
| `/resume <session_id>` | Channel 选择已有 Session；Assistant 重建能力并按当前 State 唤醒 |
| `/mcp` `/skill` | CLI 控制面，不进 Journal 当用户任务 |
| 待授权时的 yes / no | `CommandAuthorized` / `CommandRejected` |
| 待授权时的其他句子 | 仍是 `UserMessage`，下一步模型判断 |

## 两条边界

**副作用安全**：产品装配的 Tool Spec / Binding 显式声明 `requires_authorization`，签发 Command 时冻结该要求。需要授权的 Command 没有 `CommandAuthorized` 就不能 dispatch；模型不能批准自己。Runtime 不根据工具名、参数或模型措辞推断风险。

**意图**：这句话是什么意思，由下一步 Step 判断。Runtime / Assistant 不得因为“正在等授权”就丢掉用户话。

yes / no 在等待授权时由 Channel 映射为授权事实，因为那是人在回答产品的批准问题，不是模型该投的票。

MCP/Skill 安装与恢复使用 `helperme.tools.control.ControlApprovalRequest`，属于 Host 管理控制面；它不会写成 Runtime Command 授权，也不能让普通工具结果进入授权等待态。模型可以在普通对话中调用独占的 `propose_*` 控制工具。Assistant 只暂存已校验参数，待 Step 成功提交后才准备冻结方案；Channel 展示方案并把后续 `yes/no` 交给对应 Application Handler。

当前内置环境工具保持原有策略，默认不要求逐次确认；这只是产品装配当前声明，不是 Runtime 的内置白名单。以后调整某个工具的策略只改其 Spec / Binding，已签发 Command 的授权要求不会随配置变化。

## 安装

安装、恢复、更新或启用 MCP / Skill 有两种入口：直接使用 `/mcp`、`/skill`，或在普通对话中先按需加载对应管理域，再由模型提交 `propose_mcp_install`、`propose_mcp_recovery`、`propose_mcp_update`、`propose_skill_install`、`propose_skill_enable`、`propose_skill_update`、`propose_skill_repair`。管理域成功加载后，诊断与提案 Schema 从下一 Step 才可见。提案必须单独调用；用户确认前不执行变更。控制审批是当前进程中的 Assistant/Channel 状态，不恢复旧 Turn，也不侵入 Runtime Core；进程退出会放弃待确认请求，重启后必须重新提案，绝不自动执行。
