# LoopGuard：Session 级进展审视提醒

2026-09-10。首批连续重复策略已实现。本文同时取代 Self-Handoff 原有的调用次数和任务总时长预算决策；当前代码仍见 [Compact](Compact.md)。

## 职责与边界

LoopGuard 归属 Session，根据执行事实机械触发进展审视提醒。它不判定无进展，不拒绝工具调用、不强制收尾、不终止 Session，也不把策略命中转换成异常。模型依据证据决定继续原方法、调整方法、完成任务或报告阻塞；继续原方法不违反契约。

它是 Assistant 层能力，适用于普通 Session、SubAgent 和 compact Session。Runtime Core 只负责事实、冻结边界与原子提交，不理解检测策略或进展语义。compact 的来源上下文不是其自身的执行记录；各 Session 检测自己的 Journal，不混用父子会话的覆盖位置。

本轮不设计 ActivityWatchdog，不预留相关接口。单次模型调用或工具一直不返回，不由 LoopGuard 解决。

## 策略与严格匹配

机械检测策略独立演化：读取执行记录，返回命中证据或不命中，不直接发消息、调用模型或修改 Session。先使用独立策略函数和统一证据输出，不建设插件注册、动态加载或策略 DSL。

首批只实现连续相同 action。后续可增加短周期振荡、重复错误、重复结果和工具族高频；不提前实现。阈值由 `runtime.loop_guard_repeat_threshold` 配置，默认 3，配置边界要求整数且不小于 2。

相同 action 定义为相同工具身份，以及规范化后完全相同的 arguments：

- 忽略对象键顺序，递归规范化嵌套对象；保留数组顺序。
- 字符串原样保留，不 trim、不转小写、不改写路径。
- 缺失字段与显式 null 区分，不自动补默认参数。
- 不做参数语义推断或模糊匹配；保留数值与字符串的类型区别。使用确定性的 JSON 序列化；`1` 与 `1.0` 区分，布尔值与数值区分。

fingerprint 只服务于严格动作比较。错误归类、结果比较和工具族划分由各自策略定义，不扩张统一 fingerprint 的含义。

## 检测窗口与提醒覆盖

复用 Journal 事件位置，不另建执行序列。动作证据引用已提交调用及其具体 Command 身份，结果证据引用对应结果事实；一个 Step 中的多个调用仍是不同的行为。异常数量按行为计数，不用事件序号相减。

LoopGuard 统一维护提醒覆盖位置 C，各策略不维护独立覆盖游标。每次检测使用本次决策冻结快照，截至位置 P：

1. 检测窗口允许跨过 C，旧记录可帮助识别连续重复或振荡。
2. 再次触发必须在 C 之后积累足够的新异常行为；旧行为不能再次计入触发门槛。
3. 合并各策略当前命中的证据，一次提醒覆盖到 P。其他策略不能随后使用 P 及以前的旧行为再次触发。
4. 仅检测命中不推进覆盖位置；提醒随 Step 成功提交后，覆盖位置才更新为 P。

策略必须返回异常行为的位置及身份，而非只有布尔值。提醒可以引用旧证据解释模式，但新增覆盖区间为 (C,P]。

例如门槛为 3 次：A₁、A₂、A₃ 后提醒；A₄、A₅ 不重新触发；A₆ 后再次提醒。第二次可引用此前重复作为背景，但只用 A₄～A₆ 满足新增门槛。

## 决策输入与持久化

每次模型决策前，在本次冻结的 Journal 快照上检测。命中时，把独立标记块增量追加到模型上下文末尾，不修改 SYS、工具定义或已有请求前缀。示例：

```xml
<loop_guard_notice>
观察：连续 3 次调用了相同工具，规范化后的参数完全一致。
证据：……
请审视这些操作是否推进了目标，并据此决定下一步。
这是行为重复提醒，不代表已经判定无进展。
</loop_guard_notice>
```

提醒是系统提供的观察，不冒充用户新指令。已有提醒作为历史事实处理，不在每轮重新生成、改写或重复追加。

携带提醒的 Step 成功提交时，同一原子提交中记录提醒事实，保存实际文本、命中策略标识与版本、证据引用及覆盖位置。模型调用失败或 Step 未提交，不消耗提醒覆盖。事实保存在 `StepCommitted.decision_metadata.loop_guard_notice`，经 `RecordedDecision` 和既有 Step 提交链路原子落账。Runtime 只冻结、序列化不透明元数据，不解释提醒语义。

## 恢复与压缩

Journal 是唯一事实源。检测窗口与计数可重建，不另存一份权威状态。

- resume：重放完整 Journal，恢复最后已提交提醒的覆盖位置。
- 从某个 Step 重建：只采用截至该提交边界的执行和提醒事实，不带入之后的覆盖位置。此处约束重建语义，不新增历史分支操作接口。
- compact：上下文投影变化不删除执行事实，也不重置 LoopGuard。
- 策略更新：旧提醒按原事实恢复，不用新版策略重算或改写；新版策略用于后续检测，仍遵守已有覆盖位置。

## compact 调整范围

移除 compact_max_calls（默认 8 次）和 compact_timeout_seconds（默认 300 秒），删除计数预算、绝对截止时间、预算耗尽失败及最后一次调用收尾提醒等旧路径。Prompt 删除“接近预算时根据已有材料立即收尾”。不保留兼容层或双轨，并移除相关测试。

保留输入上下文预算、压缩触发阈值、读取权限与交接接纳规则。未知异常仍原样暴露，不用 LoopGuard 掩盖失败；不因提醒发布半成品或自动重试失败任务。

其他局部超时保持不变：模型 HTTP 连接/读写/连接池等待、命令执行、rg 搜索及终止宽限、MCP HTTP、Skill 下载、SQLite 锁等待。租约属于执行权协调，不属于任务总超时。

## 实施验证

先验证严格连续重复策略的完整链路，再增加策略：

- 参数键顺序不影响相同判断；数组顺序、字符串内容、缺失字段等差异不会被归并。
- 并行调用按行为计数，检测窗口可重叠，旧证据不能重复满足新增门槛；多策略共用覆盖位置。
- 提醒只追加，不改前缀；命中不限制模型继续调用工具。
- 提醒与 Step 原子提交；失败提交不推进覆盖，resume 和历史重建保持对应覆盖状态。
- 策略版本更新不改写旧提醒，compact 窗口切换不重置检测依据。
- compact 可以越过原 8 次和 300 秒限制继续工作，输入容量与局部超时规则仍有效。

实现位于 `helperme/assistant/loop_guard.py` 与 `loop_guard_strategies.py`，装配在统一决策入口；测试位于 `tests/assistant/test_loop_guard.py` 与 `test_compact.py`。

事件持久格式升级为 v4，不兼容旧事件格式；compact 表及种子删除预算字段。旧开发数据需另行备份重建，本轮不自动迁移、删除或修改用户运行数据。配置删除两项 compact 预算字段，并添加 `loop_guard_repeat_threshold`。
