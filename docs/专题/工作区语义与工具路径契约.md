# 工作区语义与工具路径契约

> 状态：开题，待设计与实现  
> 初次记录：2026-08-18  
> 定位：Phase 6D Skill 实现前的基础设施回补

## 为什么先做

MCP 管理与 Skill 设计已经同时涉及用户任务文件、Agent 持久状态、外部能力配置和进程工作目录。系统内部已经部分区分这些空间，但工具名称、参数说明和返回结果仍普遍使用模糊的 `Workspace`。

这会使模型无法稳定判断：

- 当前路径属于用户任务、Agent 状态还是宿主机文件；
- 某项内容应使用通用文件工具，还是 MCP、Skill 等领域工具；
- 命令的 `cwd`、MCP Server 的 `cwd` 与当前 Task Workspace 是否具有相同语义。

如果不先稳定这个契约，后续 Skill、MCP 恢复、Scheduler 和 SubAgent 都会继续放大路径与权限混淆。

## 待确立的语义

### Task Workspace

当前用户任务的外部事实源。通用文件工具与命令工具通过逻辑 `root + relative path` 访问它。

### Agent Workspace

HelperMe 持久状态的所有地，包括 MCP、Skill、Session 等数据。它不注册为通用文件 root，必须通过对应领域工具访问。

### Host Filesystem

`full_access` 模式下额外暴露的宿主机文件 root。它可以被通用文件工具访问，但不属于 Task Workspace，不得伪装成当前项目。

## 初步不变式

- Agent Workspace 永远不进入通用文件工具的 root 目录。
- 每个可访问 root 都必须带有模型可见的 `scope`，至少区分 `task` 与 `host`。
- 工具参数中的路径继续使用逻辑 root 和 root 内相对路径，不向模型暴露内部物理路径作为常规操作契约。
- 文件工具结果应回显可定位的 `scope/root/path`；命令工具应回显 `scope/root/cwd`。
- MCP Server 的进程 `cwd` 是 MCP 运行配置，不等于 Task Workspace。
- Skill 内容可以来自 Agent Workspace，但 Skill 脚本的任务输入输出和执行 `cwd` 仍必须显式绑定 Task Workspace。
- 工具描述不再用裸 `Workspace` 同时指代上述多种空间。

## 已观察到的缺口

- `get_workspace_info` 只返回 root 名称，不返回 scope 与访问边界。
- `WorkspaceSandboxes` 同时容纳 project root 与 host drive root，名称和实际职责已不一致。
- 文件、Git 和命令工具的 prompt 普遍使用模糊的 `Workspace`。
- 部分失败结果未回显 root/scope/path，后续诊断时上下文不完整。
- MCP 管理状态在 Agent Workspace，但当前模型可见契约没有明确告知必须使用领域工具。

## 明日起点

1. 先决定通用 root 集合的真实领域名称与最小数据结构，不先改 prompt。
2. 由 Composition Root 显式标记 `task` 与 `host` root，不通过 root 名称猜测。
3. 收紧 `get_workspace_info` 的返回契约，明确 Agent Workspace 的不可通用访问性。
4. 统一文件、命令和验证工具的参数描述与结果定位信息。
5. 用行为测试固定 scoped/full-access 两种模式的模型可见语义，再继续 Skill 实现。

## 暂不做

- 不建设统一虚拟文件系统。
- 不将 Agent Workspace 暴露为另一个通用 root。
- 不因为本次语义回补顺便重构 MCP、Skill 或命令 Runner 的内部实现。
- 不在语义契约确定前继续扩展 MCP 自纠或 Skill 执行链。
