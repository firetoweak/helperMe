# 工作区语义与工具路径契约

> 状态：设计完成，待实现
>
> 初次记录：2026-08-18
>
> 架构重审：2026-08-19
>
> 定位：Phase 6D Skill 实现前的基础设施回补

## 为什么先做

随着 MCP、Skill、Goal 和未来 SubAgent、Scheduler 的加入，HelperMe 已经同时涉及用户任务文件、Agent 持久状态、能力资源和进程工作目录。继续用一个模糊的 `Workspace` 表示这些空间，会让模型和代码都无法稳定判断路径属于哪里、应由谁访问、命令实际在哪里执行。

本专题确立的基础原则是：

> Agent 不拥有工作目录；Session 记住执行环境选择，Turn 固化执行环境绑定，Environment 承载 Task 的执行。

Task 描述要完成什么，Environment 描述在哪里、通过什么能力完成。两者相关，但互不包含。

## 领域定义

### Environment

Environment 是 Agent 能够感知并采取行动的计算世界，可以是一台机器、一个容器或一个云工作区：

```text
Environment
= 执行世界

filesystem
= 怎么触摸这个世界里的文件

shell
= 怎么向这个世界发命令

executor
= 怎么真正执行动作
```

Environment 定义自己的文件系统命名空间、路径规则、Shell 和执行能力。HelperMe Host 的操作系统、进程 cwd 和路径实现不得替另一个 Environment 解释路径。

只有计算世界本身不同，才是不同 Environment：

```text
Host
├─ container-A：独立 filesystem/env/process namespace
└─ container-B：独立 filesystem/env/process namespace
```

同一台机器上的不同工作区域不因此成为不同 Environment，而是同一 Environment 上不同的 Workspace View。

### Environment Selection

`EnvironmentSelection` 是 Session 可持久化的逻辑选择：

```text
DefaultEnvironmentSelection
├─ environment_id
├─ workspace view definition / id
└─ default_cwd
```

它只保存可序列化、可恢复的选择，不保存 socket、Shell process、filesystem client、remote executor 等活对象。

### Environment Provider

`EnvironmentProvider` 负责：

```text
EnvironmentProvider
├─ resolve EnvironmentSelection
├─ 管理 Environment 实例
├─ 建立 runtime attachment / lease
└─ 在同一 Environment 实例上重建底层连接
```

Provider 可以在连接中断后透明重连，但不得以相同配置名称悄悄切换到另一个 Environment 实例。容器被销毁后重新创建，即使名称相同，也可能是新的 Environment 实例。

第一版本地实现不必提前增加 `generation/incarnation` 字段，但 Provider 契约必须保留“重连不换实例”的语义。未来出现可重建容器或远程环境时，再补实例代际身份。

### Environment Binding

`EnvironmentBinding` 是某个 Turn 冻结的环境语义绑定：

```text
EnvironmentBinding
├─ Environment instance identity
├─ WorkspaceViewSnapshot
├─ PermissionBinding
├─ cwd
└─ runtime attachment / lease
```

冻结的是“在哪个 Environment、以什么 Workspace View、从什么 cwd 行动”，不是文件系统内容、进程状态或网络连接本身。

同一 Turn 内：

- 文件可以被修改，后续 AgentStep 必须看到新内容；
- 连接可以被 Provider 重建；
- Environment 实例、Workspace View、cwd 和授权上限不能被隐式替换；
- 所有 AgentStep、文件工具、命令工具和验证链消费同一个 Binding。

### Workspace View

Workspace View 圈定 Agent 在某个 Environment 中的工作区域，但不定义权限动作：

```text
WorkspaceViewSnapshot
└─ roots[]
   └─ RootBinding
      ├─ root_id
      ├─ scope
      └─ absolute Environment path
```

`scope` 表达空间来源，例如 `task_workspace` 或 `host_filesystem`。它不是权限。

Workspace roots 只负责：

- 路径归属；
- 模型可见工作区域；
- Permission 和 Sandbox 的空间输入；
- 生成友好的 root-relative display path。

Workspace roots 不作为普通相对路径的解析基准。

第一版如果没有可被原地修改的命名 Workspace View 注册表，直接冻结完整 roots 值即可，不提前增加 `id/revision`。真实出现后台修改命名 View 的需求后，再加入版本身份。

### Permission Binding

Permission 与 Workspace View 分离：

```text
Environment
→ 定义路径世界

WorkspaceView
→ 圈定工作区域

PermissionBinding
→ 决定能对这些区域做什么
```

同一 Environment、同一 Workspace View 可以对应不同 PermissionBinding。

Turn 冻结的是授权上限，不能因外部配置变化自动获得新权限。未来若存在实时强制撤权，则有效权限为：

```text
effective permission
= Turn PermissionBinding
∩ current mandatory policy
```

外部撤权可以使后续动作失败，但不表示 Environment Binding 已经切换。

### cwd

cwd 是当前执行上下文，不属于 Workspace View，也不是 Agent 的长期固有属性：

```text
Session
└─ default_cwd：下一 Turn 的默认选择

Turn
└─ EnvironmentBinding.cwd：本 Turn 冻结的路径解析基准
```

单次工具可以指定派生 cwd，但不能修改 Turn Binding。命令内部的 `cd` 只影响该 Shell 进程，不隐式改变后续 AgentStep 或下一个 Turn 的默认 cwd。

## 生命周期

### 总体链路

```text
Session
└─ DefaultEnvironmentSelection
       │
       ▼
EnvironmentProvider.resolve / attach
       │
       ▼
Turn
└─ EnvironmentBinding
   ├─ Environment instance identity
   ├─ WorkspaceViewSnapshot
   ├─ PermissionBinding
   ├─ cwd
   └─ runtime attachment / lease
       │
       └─ AgentStep 1..N
          └─ 一次模型调用及其直接产生的完整工具批次
```

Session 保存连续性，Turn 固化语义，Provider 管理活连接，AgentStep 消费同一 Binding。

### Turn 创建

```python
selection = (
    invocation.environment_selection
    or session.default_environment_selection
)

attachment = environment_provider.attach(selection)
binding = freeze_semantic_binding(selection, attachment)

if invocation.environment_selection is not None:
    session.default_environment_selection = selection

turn.environment = binding
```

提交顺序必须是：

```text
校验 Selection
→ 成功 resolve / attach
→ 固化 Turn Binding
→ 更新 Session 默认 Selection
→ 启动 Turn
```

- Attachment 建立失败，不更新 Session 默认 Selection。
- Turn 后续任务失败，不回滚默认 Selection；环境切换成功与任务执行成功是两个事务。
- 显式 `environment_selection` 是 sticky 的 Session 状态更新，不表示临时覆盖。
- 当前没有真实需求时，不增加 `temporary/persist/inherit` 等模式。
- 普通工具不得临时切换 Environment；需要其他 Environment 时，应由新的 Turn、Session 或未来 SubAgent 显式选择。

Session 一次最多一个 active Turn。未来若多个请求同时到达，在 Turn admission/submission queue 上按请求接受顺序串行化“更新默认 Selection + 创建 Turn”，不额外建设复杂事务系统。

## 空间划分

### Task Workspace

当前 Task 的外部事实源，保存用户输入、项目文件、任务产物和 Git 变化。Task 不进入 Environment，但由 Environment 承载执行。

### Host Filesystem

用户额外授权访问的宿主机文件区域。它可以出现在 Workspace View 中并被通用文件工具访问，但不因此成为当前项目、配置发现根或默认 cwd。

同一 Environment 中不同 Workspace View 可以暴露不同 Host 区域。只有容器、虚拟机或其他计算世界隔离才创建新的 Environment。

### Agent Home

HelperMe 的内部持久数据目录，保存 Session Artifact、MCP、Skill 和其他状态。它不是模型工作区，不注册为通用 workspace root，只能通过相应领域工具访问。

### Capability Root

Skill、Plugin 等能力包的资源位置。能力资源可以由 Environment 提供，但其安装位置不属于 Task Workspace，也不能隐式成为命令 cwd。

Skill 脚本的代码来源与任务执行位置必须分别表达：脚本来自 Capability Root，执行 cwd 来自当前 Turn Environment Binding。

## 模型可见 Environment Context

模型不应通过试探工具来猜测自己位于哪个 Environment。每个 AgentStep 的 ModelContext 都应从当前 Turn 的同一个 Environment Binding 投影环境事实。

消息角色分层为：

```text
Developer Instruction
= 定义 environment_context 的语义和使用规则

user-role contextual fragment
= 提供当前 Turn 的具体 Environment Binding 事实
```

示例：

```xml
<environment_context>
  <environment id="local" kind="host" os="linux" />

  <cwd>/repo</cwd>

  <workspace_roots>
    <root id="project" scope="task_workspace" uri="file:///repo" />
    <root id="shared" scope="host_filesystem" uri="file:///home/user/shared" />
  </workspace_roots>

  <permissions>
    <filesystem root="project" access="read_write" />
    <filesystem root="shared" access="read_only" />
    <network access="restricted" />
  </permissions>

  <shell name="bash" path="/bin/bash" />
  <current_date>2026-02-26</current_date>
  <timezone>America/Los_Angeles</timezone>
</environment_context>
```

约束：

- Environment Context 是模型可见说明，不是权限执行依据。
- Permission 只投影简明有效摘要，不注入完整底层策略实现。
- Agent Home 和 Capability Root 不因物理存在而进入 `workspace_roots`。
- Fragment 由 Runtime 生成并正确转义，不能让路径或 root 名称变成指令注入。
- 普通文件内容变化不属于 Environment Context 变化；文件事实通过工具观察。

第一版不实现 `snapshot + render_diff()`。`EnvironmentContextProjector` 在每个 AgentStep 的 ModelContext 中提供完整的当前 Turn 状态，但不把重复 fragment 累积写入 Conversation。

未来只有在真实 token 成本出现时才增加 diff。届时必须与 Safe Compression 的可见基线联动：旧 snapshot 确认可见时才能发送 diff；基线已被裁剪或压缩时必须重新发送完整 snapshot。

## Environment Path Contract

### 输入路径

```text
1. 所有文件工具路径和命令启动 cwd，都在 EnvironmentBinding
   所绑定的 Environment 路径空间中解释。

2. 相对文件 path 与相对工具 cwd，统一相对
   EnvironmentBinding.cwd 解析；命令省略 cwd 时直接使用它。

3. 绝对路径保持 Environment 原生绝对路径语义，
   不经过 HelperMe Host 的 cwd、操作系统或路径实现重新解释。

4. WorkspaceView.roots 不作为普通相对路径的解析基准，
   只负责路径归属、模型可见范围和权限边界。

5. 文件工具路径和命令启动 cwd 使用同一个
   EnvironmentPathResolver；禁止读取 Host process cwd。

6. 命令文本内部的路径由 Environment Shell 相对最终启动 cwd
   解释，不由 EnvironmentPathResolver 解析或改写。
```

因此文件工具输入收敛为普通路径：

```python
read_file(path="src/main.py")
read_file(path="/repo/src/main.py")
run_command(command="pytest ./tests", cwd="backend")
```

不再使用 `root + relative path` 作为普通文件工具的输入地址。`root` 只保留为空间归属、权限和展示元数据。

### 统一解析链

```text
Tool path / requested cwd
→ EnvironmentPathResolver
→ Environment 原生绝对路径
→ WorkspaceView root 归属判断
→ PermissionBinding 检查
→ filesystem / executor
```

相对性只存在于工具输入阶段。进入 Runtime、Result、Evidence 前必须消除相对性。

## Environment Enforcement Contract

路径解析与安全执行是两个不同职责：

```text
Path Resolution
= 确定路径指向哪里

Sandbox Enforcement
= 限制动作实际上能够触碰哪里
```

文件工具执行链：

```text
Resolver 定位
→ Workspace root 归属
→ Permission 检查
→ filesystem 操作
```

命令工具执行链：

```text
Resolver 定位启动 cwd
→ Workspace roots + PermissionBinding 物化 Sandbox Policy
→ Environment.executor 在 Sandbox 内启动进程
→ Environment.shell 解释命令文本
```

不变式：

- Runtime 不解析、不改写 Shell 命令文本，也不做字符串级安全判断。
- 命令可以包含绝对路径、`..`、`cd`、符号链接和子进程；真正限制由 Environment Sandbox 强制执行。
- 所有命令必须通过绑定当前 Environment Binding 与 Sandbox Policy 的 executor 启动，禁止直接调用 Host subprocess。
- cwd 只决定进程启动位置，不是安全隔离声明，也不表示命令副作用被限制在该目录。
- Workspace roots 定义空间范围，PermissionBinding 定义允许行为，Sandbox 负责强制落地。

在进程级 Sandbox 尚未实现时，校验 cwd 位于 Workspace 内只能证明“从合法位置启动”，不能宣称命令无法访问 Workspace 外部。实现和文档必须诚实暴露这一阶段性能力边界。

## EnvironmentLocation Contract

### 最小值对象

```python
@dataclass(frozen=True)
class EnvironmentLocation:
    environment_id: EnvironmentId
    path: EnvironmentPath
```

```text
EnvironmentLocation
= Environment 实例身份
+ 已在该 Environment 中解析完成的绝对路径
```

示例：

```json
{
  "environment_id": "local",
  "path": "file:///workspace/helperme/src/main.py"
}
```

核心不变式：

1. `EnvironmentLocation.path` 永远是 Environment 原生绝对路径，禁止保存相对路径。
2. Location 必须经过当前 Environment Binding 的 Resolver 完成解析。
3. 路径不得通过 Host cwd、Host OS 或 Host 路径规则重新解释。
4. `root_id`、workspace root、cwd、display path 不属于 Location identity。
5. Location identity 是 Environment 实例身份与 EnvironmentPath identity 的组合。
6. EnvironmentPath 的规范化、大小写、分隔符和比较语义由对应 Environment 定义。
7. Location 表达路径坐标，不自动声称两个不同路径是否指向同一 inode 或文件对象。
8. line range、stdout range、tool call id 等局部或因果信息不得塞进 Location。

面向模型或用户可以生成 native、cwd-relative 或 root-relative `display_path`，但展示路径永远不参与 identity。

### WorkspaceMembership

root 不进入 Location identity，但操作结果可以记录当次 Turn Binding 下的空间归属：

```python
WorkspaceMembership:
    root_id: str
    scope: task_workspace | host_filesystem
    display_path: str
```

它回答“本次操作通过哪个 Workspace 区域被定位和授权”，用于模型展示、审计和权限解释。Workspace View 变化不会改变资源的 EnvironmentLocation。

### 文件工具结果

```python
FileReadResult:
    location: EnvironmentLocation
    workspace_membership: WorkspaceMembership
    content: str

FileWriteResult:
    location: EnvironmentLocation
    workspace_membership: WorkspaceMembership

FileChange:
    location: EnvironmentLocation
    kind: added | modified | deleted

FileMove:
    from_location: EnvironmentLocation
    to_location: EnvironmentLocation
```

多文件操作返回逐文件 Change，不能用一个模糊 Location 代表多个资源。

失败结果在路径已成功解析时也应保留 `EnvironmentLocation`；如果失败发生在解析之前，则保留原始输入和结构化路径错误，不能伪造已解析位置。

### 命令工具结果

```python
CommandResult:
    execution_location: EnvironmentLocation
    stdout: str
    stderr: str
    exit_code: int
```

`execution_location` 只表达初始进程 cwd，不表达命令读取、写入或影响了哪些文件。Runtime 不解析 Shell command string，因此不能从 cwd 或命令文本推断资源影响范围。

### Evidence

Evidence 分开回答三个问题：

```text
Where?
→ EnvironmentLocation

Which part?
→ EvidenceSpan

How was it observed?
→ EvidenceProvenance
```

文件 Evidence：

```python
FileEvidence:
    location: EnvironmentLocation
    span: TextSpan | None
    provenance: EvidenceProvenance
    excerpt: str | None

EvidenceProvenance:
    tool_call_id: str
    tool_name: str
```

Location 与 line span 表达来源坐标，`tool_call_id` 必须能追溯到已记录的工具结果或 Runtime Artifact。Evidence 证明的是该工具调用执行时观察到的事实；文件后来变化时，不能把旧行号假装成当前事实，完成结论需要重新验证。

命令输出不是文件，不能把 stdout/stderr 伪装成 `execution_location` 下的资源：

```python
CommandOutputEvidence:
    execution_location: EnvironmentLocation
    tool_call_id: str
    stream: stdout | stderr
    span: OutputSpan | None
```

因此 Evidence origin 应允许领域分支：

```text
EvidenceOrigin
├─ FileEvidence
└─ CommandOutputEvidence
```

统一的是 `EnvironmentLocation` 值类型，不是所有结果字段的语义：

```text
FileResult.location
= 文件资源位置

CommandResult.execution_location
= 命令启动位置

Evidence.origin
= 证据来源，按来源类型解释 Location、Span 和 Provenance
```

`EnvironmentLocation` 只定位执行 Environment 中的文件系统位置。Agent Home Artifact、MCP Resource 或其他领域资源只有在确实映射为该 Environment 的文件路径时才能复用它，不能为了统一而把非文件资源伪装成 EnvironmentLocation。

## SubAgent 继承与隔离

SubAgent 应创建独立的 Session 和运行状态，但显式继承或派生父级 Environment Selection：

```text
Runtime state 隔离
Execution Environment 可共享
Filesystem 变化作为外部事实协作
```

共享 Environment 不等于共享 Conversation、Goal、Todo 或其他可变状态。需要并行写隔离时，应派生独立 Worktree、Container 或 Sandbox Environment，而不是在 Agent 状态层补文件并发规则。

SubAgent 工具仍只能消费自己的 Turn Environment Binding，不能直接借用父 Turn 的活 Attachment。

## 总不变式

- Task 描述逻辑目标，Environment 承载执行；Task 不属于 Environment。
- Session 保存可持久化 Environment Selection，不保存活 Attachment。
- 一个 Turn 只绑定一个冻结的 Environment Binding，所有 AgentStep 共享它。
- Provider 可以重建连接，但不得透明切换 Environment 实例。
- Agent 和工具不能消费无 Workspace View 与 PermissionBinding 的裸 Environment 执行能力。
- Developer Instruction 定义 Environment Context 语义；user-role contextual fragment 提供当前 Turn 事实。
- Prompt、文件工具、命令工具、验证链和 Evidence 使用同一个 Environment Binding。
- 相对文件 path 和工具 cwd 统一相对 Binding.cwd；绝对路径使用 Environment 原生语义。
- Workspace roots 不作为普通相对路径基准，只参与归属、可见性、权限和展示。
- 文件路径和命令启动 cwd 使用同一个 EnvironmentPathResolver，禁止读取 Host process cwd。
- Shell 文本由 Environment Shell 解释，Sandbox 强制执行权限；Runtime 不解析命令文本。
- EnvironmentLocation 只保存 Environment 实例身份与绝对 EnvironmentPath。
- root、scope 和 display path 是 WorkspaceMembership，不进入 Location identity。
- 命令 execution location 只代表初始 cwd，不代表副作用位置。
- Evidence 区分 Location、Span、Provenance 与 Origin，不把命令输出伪装成文件。
- 同一物理路径不应在一个 Workspace View 中以不同 scope 或 root identity 重复暴露。
- Agent Home 永远不是通用文件 root；Capability Root、Task Workspace 和权限 roots 相互关联但彼此独立。

## 设计决策与演进留痕

### 2026-08-18：最初问题

最初设计以 `Workspace` 和显式 `root + relative path` 为中心，目标是为文件工具补齐 scope，并避免命令继承 HelperMe 进程 cwd。

### 2026-08-19：层级术语对齐

项目生命周期统一为：

```text
Session → Turn → AgentStep → tool calls/results
```

Turn 表示一次用户请求的完整工作；AgentStep 表示一次模型调用及其直接产生的完整工具批次。

### 2026-08-19：Environment 成为执行世界

放弃“Agent 拥有 Workspace/cwd”的理解。Environment 定义计算世界；Workspace View 只是其中的工作区域；Task 是在这些资源上完成的逻辑目标。

### 2026-08-19：Selection、Binding、Attachment 分离

放弃 Session 保存 Default Attachment。Session 只保存可序列化 Selection；Turn 冻结语义 Binding；Provider 管理可重建的活 Attachment。

### 2026-08-19：Workspace View 与 Permission 分离

放弃“Workspace View = 授权视图”。Workspace View 只圈定 roots；PermissionBinding 决定动作；Sandbox 执行强制限制。

### 2026-08-19：cwd 归属 Turn Binding

放弃把 cwd 放进 Workspace View 或要求 Channel 每 Turn 重复维护 cwd。Session 记住默认选择，Turn 固化当前 cwd，AgentStep 共同消费。

### 2026-08-19：Environment Context 角色分层

采用稳定 Developer 语义说明与动态 user-role contextual fragment 分层。第一版使用完整当前状态投影，不实现依赖历史可见基线的 diff。

### 2026-08-19：路径输入改为 cwd-relative / Environment-absolute

放弃普通文件工具的 `root + relative path` 输入地址。文件 path 与命令 cwd 共享 EnvironmentPathResolver；相对输入基于 Binding.cwd，root 退回归属、权限和展示职责。

### 2026-08-19：解析与 Sandbox Enforcement 分离

Runtime 不解析 Shell 文本。Resolver 确定启动位置，Environment Sandbox 限制真实副作用。cwd 不是安全边界。

### 2026-08-19：统一 EnvironmentLocation 值类型

文件结果、命令执行位置和 Evidence 复用 `EnvironmentLocation`，但保留各自字段语义。Location 只包含 Environment 实例身份与绝对路径；WorkspaceMembership、Span、Provenance 和 Evidence Origin 独立表达。
