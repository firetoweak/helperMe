# Phase 0～6 回补方向

## 背景

Phase 0～6 的基础内容完成后，暂不进入后续阶段。当前实现暴露出三个需要回补的方向：执行历史、上下文脱水和 TodoList 使用价值。

本文件只保留方向、优先级和相互关系；已经形成独立问题空间的内容进入单独专题，不在此展开架构设计。

## 优先级与关系

```text
Execution Journal 与可重放执行历史
        ↓ 提供统一、可验证的历史证据
上下文脱水优化
        ↓ 提升长任务中的上下文持续性
后续后台任务 / SubAgent / Long Memory

TodoList 使用价值评估（并行观察，暂不重构）
```

前两项是当前关键方向。执行历史优先于脱水优化：如果不能固定并重放一次运行，也不能追踪信息如何产生、投影和消费，就无法可靠评价连续脱水后的运行质量。

## 方向一：Execution Journal 与可重放执行历史

最初观察到的问题是 Trace 太简单，但进一步分析后发现，Trace 只是更底层问题的一个表现：系统缺少统一、持久、可关联和可重放的执行历史。

该方向已经升级为独立专题，涉及 Conversation、State、Artifact、Checkpoint 和 Trace 的边界，并会影响未来后台任务、SubAgent 与 Long Memory。详见 [Execution Journal 与可重放执行历史](Execution%20Journal与可重放执行历史.md)。

当前方向是：先建立历史地基，使 Trace 可以由历史生成，并支持无外部副作用的片段重放；暂不把 Journal 建成所有运行状态的唯一事实源，也暂不实现崩溃恢复。

## 方向二：上下文脱水优化

当前工具脱水保留原始事实，并通过 Artifact 提供回读路径；增量摘要则会生成新的上下文状态。链路在机制上可以持续执行，但反复压缩后的语义可靠性尚不清楚。

回补目标分为三层：

- 协议正确：压缩后消息结构与工具调用链仍然合法；
- 恢复正确：脱水内容可以通过 Artifact 引用准确回读；
- 任务正确：关键约束、事实、未完成状态和决策依据没有发生不可接受的漂移。

后续优化不能只比较 token 节省量或最终是否给出答案。应先利用可重放执行历史固定模型与工具事实，再比较不同脱水策略产生的上下文和行为差异。

“完美运行”暂不作为未经定义的结论，后续需要转换成明确、分层的可验证标准。

## 方向三：TodoList 使用价值评估

TodoList 在当前真实任务中的使用频率很低，暂时不能据此判断它应当删除、增强或并入其他机制。它目前仍定位为单次复杂执行中的柔性行动参考，不是跨执行周期的任务状态或完成证据。

先通过执行历史观察：

- Todo 模式的实际触发频率和任务类型；
- TodoList 是否真实改变了执行路径；
- Todo 重写是有效重规划，还是主要形成同步负担；
- 结束屏障是否阻止过真实的不完整结束；
- 同类任务使用或不使用 Todo 时的完成质量与成本差异。

得到真实证据后，再决定保留、简化、调整触发条件或移除。当前不进行 TodoList 架构重构。

## 当前边界

- 暂不进入后续阶段；
- 暂不实现 SubAgent、后台调度或 Long Memory；
- 先建立可重放执行历史，再推进脱水优化；
- TodoList 只做观测与价值评估；
- 不为未来可能性提前建设通用分布式平台或新的规划抽象。
