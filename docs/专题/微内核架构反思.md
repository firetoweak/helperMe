# 微内核架构反思：边界、代价与演化风险

> 状态：观察中，留待后续专题评估  
> 记录时间：2026-08-14  
> 本文不属于任何 Phase，也不直接启动重构。

## 核心问题

当前项目采用微内核风格的插件架构：Core 承载稳定的 Agent 运行语义，并保持对 Goal、MCP 等具体扩展领域无感知；可选能力通过公共端口接入。

这种架构没有消灭复杂度，而是把一部分复杂度从 Core 转移到了插件协议、装配、生命周期和兼容性管理中。随着 Plugin 增多，如果扩展端口持续膨胀、Plugin 相互依赖或生命周期被统一框架过度抽象，系统可能在形式上保持“Core + Plugin”，实际上失去微内核的隔离与可替换优势。

因此，后续评估不能只看 Core 是否引用 Plugin，还要看一次能力变化会扩散到多少模块。

## 当前架构

### Core 负责

- Session、Run 与 tool-calling loop。
- 模型调用、上下文准备与 Token 预算。
- 工具契约、执行、结果外置和停止规则。
- 通用能力端口，例如 `RunHost`、`ToolsetProvider`、`ToolSpec` 和 Approval Action。
- Application 级资源进入与退出。

### Plugin 负责

- Goal Plugin：目标、Completion Contract、Executor/Judge 工作流及其状态。
- MCP Plugin：外部 Server 配置、连接、发现、调用、Secret 与安装控制面。
- Plugin 主要依赖 Core 明确公开的端口与运行契约，不把自己的领域类型反向写入 Core。

### 外层装配负责

- `console_chat.py` 作为应用装配入口，创建具体 Plugin，并处理对应的控制台交互。
- `core/composition.py` 只通过通用资源、工具、Toolset Provider 和 Approval Action 接收扩展，不认识具体 Plugin。
- Core 可以在不装配具体 Plugin 的情况下独立执行普通 Agent Run；删除 Plugin 时，只需同步删除 Plugin 自身及应用入口中的装配与交互分支。

据此，当前项目可以称为“微内核风格的插件架构”，但还不是具有统一发现、版本协商和生命周期协议的通用插件平台。

## 当前取舍

### 获得的收益

- Core 不依赖具体 Plugin，扩展领域能力可以独立演化；移除时不会要求修改 Core 运行语义。
- Goal 工作流与 MCP 外部接入没有污染基础 Run 语义。
- Core 统一掌握上下文预算、工具执行入口、通用安全策略和 Session 一致性；Plugin 负责自身领域输入与信任约束。
- 不同扩展方式可以使用小而具体的端口，不必被迫实现统一的 Plugin 基类。
- 边界可以通过依赖测试持续验证。

### 主动接受的代价

- 外层 Composition Root 必须了解各 Plugin 的具体装配方式。
- Application 生命周期需要同时管理 Core 和 Plugin 持有的资源。
- Core 必须维护足够通用的扩展端口，并承担这些端口的稳定性成本。
- Plugin 的持久安装、Application 资源和 Run 期能力加载具有不同生命周期，理解与测试成本较高。
- 扩展协议一旦被多个 Plugin 使用，修改成本会高于普通内部接口。

这些代价本身不代表设计失败。判断标准是：代价是否被限制在清晰边界内，变化是否仍然局部。

## 已出现的观察信号

`create_agent_application()` 当前已经接受多类通用扩展输入：

- `application_resources`
- `additional_tool_specs`
- `default_toolset_provider`
- `approval_actions`

它们目前都具有与具体 Plugin 无关的语义，因此没有破坏边界。但如果以后每新增一种 Plugin，都要增加一种新的注入参数，`create_agent_application()` 就会逐渐成为所有插件需求的汇总表。

另一方面，Goal 使用 `RunHost` 扩展工作流，MCP 使用 `ToolsetProvider` 扩展能力。两者的扩展方向不同，目前没有必要为了形式统一而抽象完整的 `Plugin` 协议。过早统一会把尚未出现的共同需求变成当前的框架复杂度。

## 外部对照：DeepSeek Harness 与 Cordis

DeepSeek Harness 采用比当前项目更激进的方案：底层只保留 Cordis Plugin Runtime，Session、System Prompt、Tool Registry、模型适配器和 Agent Loop 本身也由 Plugin 提供。运行中的 Harness 是按配置层叠装配的一棵 Plugin Tree；Plugin 向共享 Context 注册服务、类型化事件和 Effect，卸载时撤销对应 Effect。

参考资料：

- [DeepSeek Harness 官方仓库](https://github.com/deepseek-ai/deepseek-harness)
- [DeepSeek Harness Architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)
- [Cordis](https://github.com/cordiverse/cordis)

它与当前项目代表了两种不同取舍：

```text
helperMe
小而稳定的 Core
└─ 可选领域能力通过少量明确端口接入

DeepSeek Harness
最小 Plugin Runtime
└─ Agent Loop、Session、工具、模型和应用界面均由 Plugin 组合
```

DeepSeek Harness 最大化了替换、动态组合和产品形态定制能力，同时也把复杂度集中到了 Context、Effect、作用域、事件顺序、配置覆盖和插件兼容性上。其官方当前明确处于 Developer Preview，并提示将发生破坏兼容性的变更，这也说明全面插件化需要承担较高的协议演化成本。

当前项目不准备采用“Everything is a Plugin”：Agent Loop、Session 和 Context 仍属于稳定内核。它们共同维护基础运行语义、一致性和资源治理，拆成可替换 Plugin 暂时没有与额外复杂度相称的真实收益。

### 值得单独研究：可撤销资源注册

Cordis 的可撤销 Effect 值得从全面插件化中单独拆出来研究。它的关键不是“所有东西都是 Plugin”，而是让每次注册同时产生明确的撤销能力：

```text
mount
  ├─ 注册服务、事件监听器、工具或资源
  └─ 获得对应的撤销操作

unmount / replace
  └─ 按确定规则撤销本次 mount 产生的全部变化
```

这种机制可能带来以下价值：

- Plugin 更新或替换时，不必由装配层分别记住每一项清理动作。
- 部分装配失败时，可以撤销已经完成的注册，恢复到原状态。
- 注册所有权明确，减少旧 Handler、ToolSpec、连接或缓存残留。
- 测试可以验证 mount/unmount 前后 Registry 与资源状态一致。

当前 `application_resources` 已能通过异步上下文管理 Application 级资源，但它主要处理资源的整体进入和退出，不等同于对服务、工具、事件监听器等细粒度注册进行统一撤销。两者存在相邻需求，是否需要进一步抽象，要等真实的更新或动态替换场景出现。

后续专题应重点评估：

1. 撤销能力属于 Core 的通用资源机制，还是 Plugin Runtime 的职责？
2. Application、Session 和 Run 三种 Scope 是否应分别拥有自己的注册集合？
3. 更新时如何处理仍在使用旧能力的活动 Run：等待结束、冻结快照，还是禁止热替换？
4. 新版本 mount 失败时，旧版本是否保持可用；替换是否需要原子语义？
5. 撤销过程中发生异常时，如何既完成其他清理，又保留原始异常事实？
6. 该机制能否保持很小，只解决所有权与撤销，而不演变成完整插件框架？

当前只记录这一方向，不预先设计统一的 `PluginLifecycle`、动态热更新或依赖解析系统。

## 未来风险

### 1. 扩展端口膨胀

每个新 Plugin 都要求 Core 增加专用钩子。端口虽然名字通用，实际语义却只服务某个 Plugin，最终形成隐性的领域耦合。

### 2. Plugin 间耦合

一个 Plugin 开始引用另一个 Plugin 的类型、状态或生命周期；安装、启停或升级一个 Plugin 时必须同步修改其他 Plugin。此时复杂度不再能够随 Plugin 删除而消失。

### 3. 生命周期统一过度或不足

生命周期不足会造成资源泄漏、状态不一致和关闭顺序问题；为了覆盖所有 Plugin 而设计完整生命周期框架，又可能制造大量间接层和无效抽象。

### 4. 协议兼容性负担

公共端口被多个 Plugin 使用后，字段和行为很难直接修改。若过早承诺兼容，项目会承担尚无现实需求的版本管理成本；若随意修改，则所有 Plugin 被迫同步迁移。

### 5. Core 资源治理权被绕过

Plugin 可能要求自己的内容、工具或任务“必须执行”或“必须进入上下文”，从而绕过 Core 的 Token 预算、安全策略和停止规则。Plugin 可以定义自身领域行为，但不得绕过 Core 对共享资源、执行入口和通用安全策略的裁决。

### 6. Composition Root 退化

应用入口可能堆积大量 Plugin 特例、顺序约束和条件分支。即使 Core 源码没有导入 Plugin，系统变化仍然高度耦合。当前 `console_chat.py` 已显式承担 Goal、MCP 的创建与交互，这本身合理，但应继续观察其变化是否仍然局部。

### 7. 为插件化而插件化

把稳定的基础能力拆成 Plugin，可能只增加协议和生命周期成本，却没有获得可选、可替换或独立演化的价值。

### 8. 通用插件平台过早出现

统一 Plugin 基类、自动发现、依赖解析、版本协商和事件总线都可能合理，但只有真实重复需求出现后才值得引入。提前建设会让学习目标从 Agent 架构偏移到插件框架开发。

## 后续专题评估问题

未来出现新 Plugin，或者现有扩展端口发生明显变化时，逐项回答：

1. 删除该 Plugin，是否只需删除 Plugin 自身和外层装配代码？
2. 新增该 Plugin，为什么必须修改 Core？新增的是与具体 Plugin 无关的核心能力，还是 Plugin 专属需求？
3. 一个 Plugin 是否知道另一个 Plugin 的领域类型、存储或生命周期？
4. 某项协议是否已经有至少两个真实使用方？共同语义是否稳定？
5. Plugin 是否遵守 Core 对共享资源、执行入口和通用安全策略的裁决，同时自行守住领域输入与信任边界？
6. Application、Session、Run 和持久安装四种生命周期是否被明确区分？
7. 一次协议变化需要同时修改多少模块和测试？
8. Composition Root 是否出现不断增长的 Plugin 专属参数、顺序规则或条件分支？
9. 当前抽象是在消除已经发生的重复，还是在预测未来？
10. 新增复杂度能否随对应 Plugin 一起删除？

## 建议关注的触发条件

出现以下情况之一时，再启动正式架构评估，而不是立即重构：

- 第二个 Plugin 需要与现有 Plugin 相同的资源生命周期能力。
- 出现 Plugin 原地更新、替换或部分装配失败后的回滚需求。
- 第二个 Plugin 需要向上下文提供候选内容。
- `create_agent_application()` 再次因为单个 Plugin 增加新的注入类别。
- Plugin 开始直接依赖其他 Plugin。
- 某个公共端口需要维护多个并存版本。
- Plugin 的启停、升级或删除需要修改 Core 状态。
- 外层装配的 Plugin 条件和顺序已经难以通过局部测试说明。

## 当前结论

当前架构仍保有微内核的主要优势：Core 可在不装配具体 Plugin 时独立运行，Plugin 主要依赖公开契约，移除扩展不需要改变 Core 运行语义。默认应用入口仍显式装配 Goal、MCP，因此这里的“可移除”是边界清晰、修改局部，而不是删除目录后应用入口无需调整。

现阶段的主要风险不是 Plugin 数量，而是扩展端口、跨 Plugin 关系、应用装配和生命周期协调是否随数量形成耦合网络。Hermes 一类成熟系统表明，自动发现、统一注册、Hook、中间件和兼容机制可以支撑丰富生态，也会让插件平台本身成为新的复杂子系统。当前项目尚未出现这种现实需求，不必提前承担相同成本。

当前不引入统一 Plugin 框架，也不因潜在风险提前重构。继续使用小而具体的公共端口，并以“变化是否局部、复杂度能否随 Plugin 删除”为主要观察指标。待上述触发条件真实出现后，再做专题评估并决定是否提炼协议。
