# Execution Journal 与可重放执行历史

> 状态：历史方向讨论稿，已停止作为实施依据。本文用于保留问题来源和架构推演过程。
>
> **方向更新（2026-08-21）**：继续推演后，Execution Journal 已从“运行后的可重放历史”提升为新 Agent Runtime 的事实骨架。以下正文按旧架构语境原样保留，其中“Runtime State 独立驱动”“做到 L2 后停止”和“L3 后置”等表述均不再作为现行结论或实现边界。新的唯一权威架构决策见 [Agent Runtime 状态推进模型](Agent%20Runtime状态推进模型.md)。

## 1. 背景

一个长期运行的智能系统会不断产生对话消息、模型调用、工具执行、外部结果、状态迁移、暂停与恢复等事实。只保存当前状态，无法解释系统如何到达当前位置；只保存面向调试的日志，又不足以稳定重现历史。

当系统进一步支持上下文压缩、后台任务、多执行单元协作和长期记忆时，分散的运行记录会带来几个共同问题：

- 同一事实在多个模块重复保存，彼此可能不一致；
- 只能看到结果，无法追踪产生、消费和状态变化之间的因果关系；
- 重新运行会再次访问模型、工具或外部系统，难以进行稳定对照；
- 长时间暂停或进程重启后，难以判断哪些动作已经发生；
- 长期记忆缺少稳定来源，无法重新提取、纠错和追溯。

本专题考虑建立一个通用的执行历史地基：**Execution Journal**。

## 2. 核心方向

Execution Journal 是按确定顺序追加的执行事实集合。它保存“发生过什么”，并为每个事实提供稳定身份、历史位置和必要的因果关系。

第一阶段希望达到：

- 执行历史能够持久保存和增量读取；
- 对话、模型、工具、状态变化等事实能够位于同一历史坐标中；
- 大内容通过稳定 Artifact 引用保存；
- Trace 可以由历史重新生成；
- 已记录片段可以在不重新触发外部副作用的前提下重放；
- 为未来 Checkpoint、后台任务、SubAgent 和 Long Memory 留下自然边界。

第一阶段不要求 Journal 成为所有运行状态的唯一事实源，也不要求从任意历史位置恢复并继续真实运行。

## 3. 概念模型

```text
                     Execution Journal
                 顺序、身份、因果与历史事实
                            │
          ┌─────────────────┼─────────────────┐
          ↓                 ↓                 ↓
    Conversation       Checkpoint          Trace
     协议事实视图        恢复位置与快照        观测分析视图
          │                 │                 │
          └─────────────────┴─────────────────┘
                            │ 引用
                            ↓
                      Artifact Store
                       外部大内容

Runtime State：独立持有当前有效状态，并驱动下一步运行。
```

建议的最小历史信封是：

```text
JournalEvent
├─ event_id          稳定事件身份
├─ stream_id         所属执行历史
├─ sequence          流内权威顺序
├─ event_type        事实类型
├─ causation_id?     直接原因
├─ occurred_at       发生时间
├─ schema_version    载荷版本
├─ payload           有界结构化事实
└─ artifact_refs     可选的大内容引用
```

具体字段仍需在实现前验证。核心要求是能够稳定排序、引用、增量读取和表达直接因果，不预先建设通用分布式追踪模型。

## 4. 概念边界

### 4.1 Journal 与 Conversation

Conversation 保存参与者之间的协议事实，例如用户消息、模型消息、工具调用和工具结果。它主要服务后续模型交互和上下文投影。

Journal 保存更广泛的执行事实，例如上下文如何准备、模型调用是否重试、工具执行何时开始、状态为何变化以及运行如何结束。

两者的关系是：

> Journal 确定事实在执行历史中的位置；Conversation 确定哪些事实组成合法的交互协议。

Conversation 不应成为 Journal 的完整副本，Journal 也不应把所有运行记录注入模型上下文。删除 Trace 不应影响 Conversation；丢失 Conversation 协议事实则会影响后续交互。

### 4.2 Journal 与 State

State 表示系统当前是什么样，负责驱动下一步运行；Journal 表示系统怎样变成现在这样，负责保存历史证据。

```text
旧 State
    ↓ 动作
新 State ─────→ 驱动后续运行
    │
    └────────→ Journal 记录动作与状态迁移事实
```

第一阶段不通过扫描 Journal 隐式推导当前 State，也不要求所有 State 都能由 Journal 重建。否则会立即进入完整 Event Sourcing，需要承担事件迁移、重放幂等和多版本兼容等额外复杂度。

### 4.3 Journal 与 Artifact

Journal 适合保存有界的结构化事实，不适合直接承载大型模型请求、工具正文、文件内容或状态快照。

Artifact Store 独立保存大内容，Journal 保存稳定引用、内容哈希、类型和来源。这样既能保持历史轻量，也能在重放时验证引用内容是否仍然一致。

Artifact 的权限、保留期和删除策略仍由 Artifact 生命周期负责，不能因为被 Journal 引用就默认永久保留。

### 4.4 Journal 与 Trace

Trace 是面向观测和分析的历史投影，可以表现为时间线、因果树、指标或诊断报告。Journal 是生成这些视图的稳定历史来源。

```text
Journal
  → 按 stream 或 scope 筛选
  → 按 sequence 排序
  → 按 causation 组织
  → 按需展开 Artifact
  → Timeline / Causal Tree / Metrics
```

Trace 可以删除后重建，不参与运行决策，也不能成为隐藏的状态所有者。

### 4.5 Journal 与 Checkpoint

严格意义上的 Checkpoint 表示：在 Journal 的一个确定位置，对可恢复 State 所做的稳定快照。

```text
Checkpoint
├─ journal_position
├─ snapshot_reference
├─ state_schema_version
└─ resume_semantics
```

因此依赖关系是：

```text
Checkpoint = Journal 历史位置 + State Snapshot + 恢复契约
```

模型用量、上下文准备、阶段完成、审批请求和错误记录本身只是事件、通知或结果，不应因为“值得记录”就统称为 Checkpoint。

第一阶段只需让 Journal 能表达和定位未来的 Checkpoint；真正的状态恢复在出现后台任务或崩溃恢复需求后再实现。

## 5. 重放语义

“重放”至少包含两种不同操作，必须明确区分。

### 5.1 历史重放

使用已经记录的模型响应、工具结果和外部信号重新构建某段历史，不再次调用外部系统，不重复产生副作用。

它适合：

- 生成 Trace；
- 重建 Conversation 片段；
- 比较不同上下文投影或压缩策略；
- 重跑评估器与长期记忆提取器；
- 复现错误发生前的决策输入。

### 5.2 重新执行

重新调用模型、工具或外部系统。结果可能变化，也可能重复写文件、发送消息或执行其他副作用。

重新执行应创建新的执行分支，并显式引用原历史，不能冒充原历史重放。第一阶段不建设通用的分支执行机制。

### 5.3 可重放的边界

若要稳定重放一个片段，Journal 必须记录该片段依赖的非确定性输入，例如：

- 用户或外部系统输入；
- 模型实际响应；
- 工具实际结果；
- 审批、取消和中断决定；
- 必要的模型、配置、能力及版本引用；
- Artifact 引用与内容校验值。

“记录全部历史”不是记录所有内存变量或函数调用，而是记录足以解释和重现目标行为的事实边界。

## 6. 预期收益

### 6.1 Trace 与诊断

- 从模型决策追溯到实际使用的上下文；
- 从工具结果追踪到后续消费它的决策；
- 解释状态变化、重试、停止和恢复的直接原因；
- 用多种视图分析同一历史，不在各模块重复组装日志。

### 6.2 上下文管理与压缩

固定同一份模型响应和工具结果后，可以对相同历史运行不同上下文策略，比较协议正确性、Artifact 恢复能力、token 构成和关键事实保留情况。

Journal 不负责压缩算法，但能提供稳定、可重复的验证输入。

### 6.3 后台任务

后台任务会跨越时间、进程和外部信号。持久历史可以记录任务何时开始、为何等待、信号是否消费、动作是否执行以及恢复前处于什么位置。

在未来的 Durable Runtime 中，Checkpoint 与后续 JournalEvent 可以用于恢复 State。Journal 仍不能单独保证外部副作用恰好执行一次，具体动作还需要幂等键、事务或执行后验证。

### 6.4 SubAgent 与多执行单元

稳定的 stream、scope 和因果引用可以描述父任务为何创建子执行、子执行产生了什么结果，以及结果被谁消费。

Journal 只提供历史关联，不负责委派策略、权限隔离、资源调度和结果整合。

### 6.5 Long Memory

Journal 保存完整但嘈杂的经历；Long Memory 保存从经历中提炼出来、值得未来复用的知识。

```text
Execution Journal
        ↓ 提取、验证、合并
Long Memory
```

Memory 可以引用来源事件，从而支持出处追踪、重新提取、冲突检查、纠错和失效。Journal 不应直接作为模型的长期记忆上下文，也不负责记忆选择、检索和遗忘策略。

### 6.6 评估与回归

同一历史可以重复运行新的 Trace 投影、压缩策略、评估器和 Memory Extractor，减少模型与工具随机性对实验结论的干扰。

## 7. 建设等级

### L1：可观测历史

- 稳定事件身份与顺序；
- 有界结构化载荷；
- scope 与直接因果；
- 持久化和增量读取；
- 从 Journal 生成 Trace。

### L2：可重放历史

- 记录目标片段需要的非确定性输入与结果；
- Artifact 内容可校验回读；
- 不访问外部系统即可重放历史片段；
- 相同历史可以供不同投影和评估策略复用。

### L3：Durable Runtime

- State Snapshot；
- 真正的 Checkpoint；
- Checkpoint 后事件重放；
- 进程重启后的恢复与继续；
- 外部信号消费和副作用幂等边界。

当前建议做到 L2 后停止。L3 等后台任务或崩溃恢复出现真实需求后再进入。

## 8. 当前实施方向

概念与实现顺序应分开：

```text
澄清 Checkpoint、Event、Notice、Outcome 的语义
        ↓
盘点现有运行事实，确定最小事件集合
        ↓
建立最小 Journal 与 Artifact 引用
        ↓
打通一个完整执行周期的垂直切片
        ↓
从 Journal 生成 Trace
        ↓
完成一次无副作用片段重放
        ↓
停止并重新评估
```

真正的 Checkpoint 实现依赖 Journal 的稳定历史位置，因此放在 Journal 之后；但在设计 Journal 之前，必须先澄清 Checkpoint 语义，避免把现有通用运行记录原样搬入 Journal。

## 9. 第一阶段停止边界

满足以下能力后停止扩张：

1. 一次完整执行能够形成顺序明确的持久 Journal；
2. Conversation 能取得合法、完整的协议事实；
3. 大内容通过 Artifact 引用保存，并能校验回读；
4. Trace 能只依赖 Journal 和 Artifact 生成时间线与因果关系；
5. 不重新调用模型和工具，能够重放一个已记录片段；
6. 同一历史能够比较两种上下文投影或压缩策略；
7. 进程重启后仍能读取 Journal 与 Artifact；
8. 删除 Trace 投影不改变运行语义；
9. 当前 State 仍由各自领域对象持有和驱动，不通过扫描 Journal 隐式恢复；
10. 没有为了未来模块引入其领域逻辑。

一句话边界：

> 做到“历史可持久、事实可关联、片段可重放、视图可重建”就停止；“状态可恢复并继续执行”留给 Durable Runtime。

## 10. 第一阶段明确不做

- Journal 成为所有 State 的唯一事实源；
- 从 Journal 重建全部 Session、任务或工具状态；
- 进程崩溃后的自动恢复；
- Scheduler、Watcher、Timer 和后台任务状态机；
- Long Memory 的提取、检索和遗忘；
- SubAgent 的委派、权限和调度；
- 外部副作用的 exactly-once 保证；
- 任意代码版本之间的确定性重放；
- 通用分布式事件平台或 Trace UI；
- 为所有未来模块预先设计事件类型。

## 11. 需要继续讨论的问题

> 更新说明：Journal 权威范围、Conversation/State/Checkpoint 的核心关系以及 L2/L3 边界已由新架构决策重新回答。本节只保留历史问题清单；仍然开放的主要是 Stream 与产品对象映射、Artifact 保留策略、Schema 演进范围和第一条垂直切片的具体实现。

以下问题暂不在方向稿中冻结：

- Journal 的权威范围：哪些事实只能存在一份，哪些只是引用或投影；
- stream 与 scope 的最小模型，以及父子执行关系何时进入；
- Conversation 是直接保存的领域记录，还是由统一历史投影得到；
- 哪些状态迁移必须记录，哪些只属于模块内部实现；
- 模型请求、工具结果和状态快照何时内联，何时进入 Artifact；
- Journal 与 Artifact 的保留、删除、隐私和权限一致性；
- 事件 Schema 的兼容策略与允许支持的重放版本范围；
- 第一条真正 Checkpoint 的恢复对象和安全边界。

这些问题应通过一个真实垂直切片逐步收敛，而不是一次性设计完整答案。
