# 个人助手的可控扩展：功能演化、边界与抽象成本

> 状态：长期原则，随真实功能演化持续校准  
> 初次记录：2026-08-14  
> 重新定位：2026-08-17  
> 本文不属于任何 Phase，也不直接启动重构。

## 项目立场

HelperMe 是一个由个人拥有、理解并持续塑造的通用助手，不是面向未知用户和未知产品形态的通用 Agent Framework。

项目通过亲手构建真实可用的助手来学习和拆解 Agent。学习是构建方式，最终结果仍应当能够长期使用。架构设计既要容纳真实功能增长，也必须保证增长后的系统仍能由一个人理解、修改和验证。

因此，本专题的核心问题不是“如何设计纯粹的微内核”，而是：

> 新增一个对个人助手有价值的功能时，能否局部接入、明确生效、独立验证，并且不引入服务于未知使用者的通用机制？

## 最高原则

> 功能能够持续生长，而复杂度仍由一个人掌控。

这里的“掌控”至少包含三层：

- 认知掌控：能够解释系统为何产生当前行为。
- 运行掌控：状态、权限、能力激活和失败不会暗中发生。
- 演化掌控：需求变化时知道改哪里、如何生效，并能验证影响范围。

“高内聚、低耦合、可扩展”仍然重要，但必须用实际变化检验：

- 高内聚不是类拆得细，而是同一变化原因集中在一起。
- 低耦合不是依赖箭头少，而是一个需求变化影响的模块少。
- 可扩展不是预留大量接口，而是明确规划的新功能到来时修改局部。
- 好抽象不是层级多，而是用更少概念解释更多已经出现的事实。

## 产品、架构与审美理由

每项重要抽象应明确主要理由，避免把偏好包装成必需：

```text
Product       没有它，真实使用场景无法可靠完成
Architecture  没有它，已经出现的变化会扩散或边界会混乱
Exploration   为了学习或验证一种架构思想而主动实验
```

三种理由都可以成立。探索性抽象不是错误，但不应未经验证就成为产品主链路的长期负担。

## 扩展范围

HelperMe 只为已经发生或路线中明确规划的功能变化建立边界：

```text
已经遇到的需求        立即设计并验证
路线中明确将做的功能  保留接入方向，不预建完整框架
想象中的可能性        暂不抽象
第三方未知需求        明确不负责
```

“可扩展”在本项目中的含义是：能够自然长成未来想要的个人助手，而不是能够承载任意人的任意 Agent。

## 不同功能使用不同的窄端口

当前可预见的扩展方向并不共享同一种变化原因：

| 功能方向 | 主要变化 | 当前或候选边界 |
|---|---|---|
| 外部工具与服务 | 能力发现、加载与调用 | `ToolSpec`、`ToolsetProvider` |
| 复杂目标工作流 | 跨 Run 组织与完成判断 | `RunHost` |
| Skill | 指令、知识与工作流的按需加载 | 独立 Skill 加载边界，待真实设计 |
| Web | 搜索、读取及证据回写 | 独立工具契约与 Provider 适配 |
| Scheduler / Watcher | 对话外的触发与任务启动 | Task Trigger 边界，待真实设计 |
| SubAgent | 委派、隔离执行与结果回收 | Delegation 契约，待真实设计 |
| Memory | 跨 Session 的可选事实来源 | 独立 Store 与显式注入，后置 |

这些能力可以共同复用 Core 的运行语义，但不因为“都是扩展”就强行实现统一的 `Plugin` 基类、生命周期或发现协议。只有两个以上真实功能出现稳定共同语义后，才考虑提炼更高层抽象。

## Core、产品能力与 Plugin

三者表达不同问题：

```text
Core      所有受支持 Agent Run 都必须维护的稳定不变量
Product   默认个人助手为了真实可用而需要的完整能力
Plugin    某项能力在代码中的隔离与装配方式
```

Plugin 只说明架构位置，不说明产品重要性。Web、Goal 可以不属于 Core，却可以是默认产品的重要能力。

Core 当前主要负责：

- Session、Run 与 tool-calling loop。
- 模型调用、上下文准备与 Token 预算。
- 工具契约、执行、结果外置、证据回写和停止规则。
- Application 级资源进入与退出。
- 已被真实功能需要的小而明确的公共端口。

具体能力负责自己的领域模型、状态与信任边界，不把领域名词反向写入 Core，也不得绕过 Core 对共享资源、执行入口和通用安全策略的裁决。

## 可控扩展的五项要求

### 1. 变化局部

一个功能变化应有明确所有者。修改不应无理由扩散到 Core、其他能力和多个装配层。

### 2. 生效路径明确

从持久配置到模型实际可见能力的路径必须可以说明。以动态工具为例：

```text
持久配置
→ Application 装配与资源进入
→ Session 能力快照
→ Run 期加载
→ Tool Registry
→ 当前模型轮次可见
```

任何一层没有生效，都应保留明确事实，不用静默 fallback 掩盖。

### 3. 结果可以验证

系统应能回答“本次 Run 实际使用了什么、从哪里加载、为什么没有加载”。自动化测试既验证功能结果，也验证关键生命周期和装配路径。

### 4. 失败可以定位

异常保留原始语义；日志与 Trace 应帮助定位断点，而不是只报告最终的“能力不可用”。增加抽象层时，必须同时考虑跨层因果链如何观察。

### 5. 复杂度可以移除

能力被删除后，其领域状态、装配分支和专属复杂度应能一起删除。公共端口只有在仍有真实使用方时才保留。

## 当前架构的有效部分

- Goal 工作流与 MCP 外部接入没有污染基础 Run 语义。
- Goal 使用 `RunHost`，MCP 使用 `ToolsetProvider`；两者变化方向不同，没有为了形式统一而创建完整 Plugin 协议。
- Session 冻结能力快照，配置变化后明确过期，避免旧 Run 静默切换能力版本。
- Core 统一掌握上下文预算、执行入口和通用停止规则，具体能力守住自身领域边界。
- Web 第一版只接单一实现，不预建 Provider Registry、自动探测、fallback、Browser、Crawl 和专属持久 Cache。
- 依赖边界和真实运行闭环都有对应测试或 Benchmark。

这些设计的价值不在于“符合微内核”，而在于它们提高了功能变化的局部性和运行行为的可解释性。

## 当前风险

### 1. 装配层增长

`create_agent_application()` 当前接收 `application_resources`、`additional_tool_specs`、`default_toolset_provider` 和 `approval_actions` 等扩展输入。它们目前具有通用语义，但如果以后每新增一个功能都增加一种注入类别，Composition Root 会变成所有能力需求的汇总表。

### 2. 代码隔离但运行不透明

Plugin 目录清晰不代表能力已经可控。持久安装、Application 资源、Session 快照、Run 加载和逐轮工具可见性具有不同生命周期；链路增长后，最容易重新出现“改后不生效且原因不明”。

### 3. 为统一而统一

Goal、MCP、Skill、Scheduler 和 SubAgent 的变化方向不同。统一 Plugin 基类、事件总线、依赖解析、版本协商和完整生命周期，可能只获得形式一致，却增加主链路理解成本。

### 4. 抽象先于事实

只有一个实现时提前建设 Registry、Provider 选择、自动探测或 fallback，会把想象中的变化变成当前必须维护的机制。

### 5. 局部优雅、全局难追踪

每层接口都可能单独合理，但过长的 `接口 → Provider → Composition → Snapshot → Registry → Runtime` 因果链会削弱整体掌控。新增间接层必须换来真实的变化隔离或可替换价值。

### 6. Plugin 间耦合

一个能力开始引用另一个能力的领域类型、状态或生命周期时，复杂度不再能随功能删除。跨能力协作应优先通过已有 Core 事实或窄用例端口完成。

## 对外部框架的使用方式

DeepSeek Harness、Cordis、Hermes 等通用框架可以用来观察能力边界、资源所有权和生命周期问题，但 HelperMe 不以复制其扩展规模为目标。

“Everything is a Plugin”、自动发现、统一事件系统、版本兼容和任意产品形态组合，主要服务框架使用者，不是当前个人助手的需求。只有其中某个局部机制直接解决已经出现的问题时，才单独吸收。

例如，可撤销资源注册只有在真实出现原地更新、部分装配失败回滚或注册残留后，才值得专题评估；当前不预建统一 `PluginLifecycle` 或动态热更新系统。

## 新增抽象前的检查

1. 它服务哪个已经发生或明确规划的个人助手功能？
2. 当前变化原因是什么，应该由哪个模块拥有？
3. 没有该抽象时，修改实际会扩散到哪里？
4. 它是在消除已经出现的重复，还是预测未知需求？
5. 能否用更小、更具体的端口解决？
6. 从配置到当前 Run 的生效路径是否仍能完整说明？
7. 系统如何证明本次实际使用了它？
8. 失败时能否定位到具体生命周期或装配阶段？
9. 删除对应功能时，这部分复杂度能否一起删除？
10. 这是 Product、Architecture 还是 Exploration 理由？

## 触发重新评估的条件

出现以下事实之一时，再设计对应机制，不因想象中的框架需求提前建设：

- 第二个真实功能需要相同且稳定的扩展语义。
- 一次功能变化开始无理由扩散到多个领域模块。
- 当前 Trace 无法判断能力在哪一层没有生效。
- 出现原地更新、替换或部分装配失败后的真实回滚需求。
- `create_agent_application()` 再次因单个功能增加专属注入类别。
- 两个能力开始直接依赖彼此的领域状态或生命周期。
- 外层装配的条件和顺序已经难以通过局部测试说明。
- 某个公共端口已没有真实使用方，或只剩一个被过度包装的实现。

## 当前结论

HelperMe 不追求通用插件平台，也不把 Core 尽可能小当作目标。当前继续保留稳定的 Agent 运行语义，并让不同功能通过小而具体的边界接入。

后续架构评估首先观察三件事：变化是否局部、生效是否明确、结果是否可验证。微内核、Plugin 和其他架构模式只作为实现手段，不作为项目身份或设计终点。

> 不追求通用可扩展，只为个人助手已经发生或明确规划的功能变化建立窄抽象；不同变化方向不强行统一。
